# case-08 · 会话恢复仪式（orientation）

| 项 | 内容 |
|---|---|
| 测什么 | 新会话面对已有库时，是否**先读后动**（SCHEMA → HOME → log 末 30 行） |
| 输入 | case-01 产物库 + 一句"帮我再沉淀一份材料" |
| 判分 | 人工核对行为轨迹（是否读了三个文件、引用是否准确） |

## 期望行为

1. 先读 `SCHEMA.md`（拿到 4 个领域配置）→ 读 `HOME.md`（知道已有 7 条目 2 案例）→ 读 `log.md` 末 30 行（知道上次做到哪）。
2. 回答里能体现"已知"：例如"我看到现有 4 个领域，最近一次是 11-10 的入库，本次材料看起来属于广告投放"。
3. 条目 >100 时先用 Grep 搜关键词再决定新建/更新（本例 7 条，不触发）。

## 反例（FAIL）

- 直接开始写新条目，不读任何既有文件（后果：重复建页、链接指向不存在的标题）；
- 只读了 SKILL.md 就当作读了库（SKILL 是方法，不是内容）；
- 声称"已恢复上下文"但说不出当前有几个领域、几条条目。

## 为什么必须有这条

换会话即失忆是 agent 做知识库最大的工程风险。SKILL 用"强制先读后动"的仪式来对冲，这条 case 就是验证仪式有没有真的执行——它机器测不了，只能看行为轨迹。
