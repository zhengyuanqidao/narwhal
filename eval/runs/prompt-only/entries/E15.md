## 一句话结论

GitHub 在一次大 MySQL 表 schema 迁移的**最后一步 rename** 时，相当一部分只读副本进入信号量死锁，转入崩溃恢复，把负载推给健康副本，级联到没有足够副本处理生产请求，核心服务可用性受损。

## 展开与个人判断

原文事实：GitHub 平台在处理大 MySQL 表的 schema 迁移时遇到新失败模式；迁移常需数周完成，最后一步是 rename 把更新后的表移到位。这一步期间，相当一部分 MySQL 只读副本进入信号量死锁。集群由主节点承担写入、多个只读副本承担生产流量，另有若干副本服务备份与分析等内部读流量。陷入死锁的副本进入崩溃恢复，增加健康副本负载；因级联性质，活跃副本不足以处理生产请求，影响核心服务可用性。

我的判断：迁移最危险的往往不是「搬数据」，而是**收尾切换那一刻的全局同步动作**。rename 看起来是元数据操作，却让所有副本在同一瞬间经历相同的状态转换；它们同时抖动，就没有 spare capacity 接管。我要的是：切换分批、保留专门的只读副本池不参与迁移、并在切换前压测「N 个副本同时挂掉」的场景。跨副本状态一致性还牵涉成员/主节点问题，见 [[双 leader 双 controller：ZooKeeper 重供给引发的脑裂]]；另一类迁移类型问题见 [[INT32 天花板：9 小时 48 分与 76% 的签发失败]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：分批切换会延长迁移总时长，在变更窗口紧张时不被接受；但一次全量切换的尾部风险更高。
- 边界：小表迁移的 rename 几乎瞬时，不必套用大表的分批纪律；这条针对「迁移耗时数周、副本众多」的场景。
- 反例：保留专用副本池会降低资源利用率，被成本优化砍掉后，迁移就失去缓冲——这正是 Buildkite 那种「为省 AWS 开支降容量」的同类错误。

⭐ 迁移的收尾 rename 是同步动作——所有副本同时抖动时，你需要的 spare capacity 正好不存在。
