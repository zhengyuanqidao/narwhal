## 一句话结论

第 27 个闰秒（`2016-12-31T23:59:60Z`）带来的时间倒流，让 Cloudflare 的加权轮询 DNS 在某些 CNAME 查询上 panic——因为 Go 的 `time.Now()` 被错误假设为单调，负值灌进 `rand.Int63n()` 触发 panic；Linux 上同一个闰秒则分别造成 `xtime_lock` 死锁和定时器提前一秒到期。

## 展开与个人判断

原文事实：Cloudflare 因跟踪第 27 个闰秒产生的时间倒流，RRDNS 的加权轮询在某些 CNAME 查找上 panic；Go 的 `time.Now()` 被错误假设为单调，向 `rand.Int63n()` 注入负值导致 panic。Linux 一例中，闰秒代码在持有 `xtime_lock` 的定时器中断处理函数里调用 `printk`，唤醒的 `klogd` 有时取时间而等待 `xtime_lock`，形成死锁。另一例中 2012 年闰秒把 `CLOCK_REALTIME` 回拨一秒但没有更新 `hrtimer base.offset`，使 `TIMER_ABSTIME` 定时器提前一秒到期，包括设定少于 1 秒的定时器；应用中少于 1 秒的 sleep 循环变成忙等，高负载让大量 Web 服务在 2012 年宕机。

我的判断：三种死法共享一个错误前提——**把墙上时钟当成单调时钟**。墙上时钟会跳、会回拨、会插入闰秒；单调时钟只前进。我要的是硬隔离：计时/超时/随机数种子只用单调时钟，需要展示时才转墙上时间；并且在持锁路径上禁止任何可能回调的日志操作。那个忙等还说明第二层问题：失败重试会放大负载，见 [[重试把恢复变成二次灾难：惊群与重试风暴]]。日期算术那类同根问题见 [[自己写「加一年」：闰日证书把 Azure 打趴一天]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：不是所有场景都该用单调时钟——跨机器对齐时间、证书校验、日志时间戳必须用墙上时钟（通常是 UTC）。
- 边界：闰秒可以被「 smear」（把多出的一秒摊到一天里）规避，但 smear 会让不同实现对「当前时间」短暂不一致，跨系统对账要留意。
- 反例：把 `printk` 全禁掉不现实；正确做法是缩短持锁区间、把日志挪到锁外，而不是放弃可观测性。

⭐ 墙上时钟会倒着走——凡是需要「只会前进」的地方，改用单调时钟，没有例外。
