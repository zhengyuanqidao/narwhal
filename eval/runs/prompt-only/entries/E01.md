## 一句话结论

把「最小健康主机数」这种安全下限交给配置默认值兜底，等于把保险丝拆了还以为装着——Amazon 首尔区域一次配置变更删掉了该设置，fleet 掉到很低的默认值，in-VPC DNS 查询失败约 **84 分钟**。

## 展开与个人判断

原文事实：一次配置变更错误地移除了指定 EC2 DNS resolver fleet 最小健康主机数的设置，系统回落到非常低的默认值；健康主机数下降后，EC2 实例的 in-VPC DNS 查询失败约 84 分钟，直到人工恢复容量。事后的 remediations 是加了**语义配置校验**和对主机移除的**按小时限流**。

我的判断：这里真正的坑不是「改错了」，而是「删掉配置项本身是合法的」。删除一个键和把它设成危险值，在语法校验层看起来都是合法操作；只有语义校验才知道「这个 fleet 的最小健康数不能低于 N」。同理，按小时限流不是为了防止配错，是为了给人类反应时间——把瞬时可造成的破坏上限定死。我把这条和 [[无灰度：一条全局配置变更如何打穿全网]] 放在一起看：一个是缺语义校验，一个是缺渐进发布，都是「配置系统把危险操作当普通操作」。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：不是所有配置项都需要语义校验。纯展示类、无安全下限的开关加语义校验只会拖慢发布，别一刀切。
- 边界：按小时限流只争取时间，不阻止故障；若恢复流程本身依赖被限流的 API（参见 [[重试把恢复变成二次灾难：惊群与重试风暴]] 里恢复信号变放大器的情形），限流反而会卡住救援。
- 反例：如果 fleet 本身有 admission control 能拒绝低于阈值的缩容，就不需要在配置层重复做；重复校验会带来两套阈值不一致的新故障。

⭐ 删配置项和配危险值是一回事——语义校验要管的是「下限不能被拿掉」，不是拼写。
