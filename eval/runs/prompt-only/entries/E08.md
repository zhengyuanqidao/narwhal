## 一句话结论

两个冗余的 DNS Enactor 进程竞态：一个异常延迟，另一个应用了更新计划并做清理，此时被延迟的那个用旧的过期计划覆盖了区域端点 `dynamodb.us-east-1.amazonaws.com`，cleanup 随即把这条记录删掉——空记录引发约 **15 小时**级联，波及 EC2、NLB 和 Lambda。

## 展开与个人判断

原文事实：DynamoDB DNS 管理中的潜伏竞态让区域端点留下空记录。两个冗余「DNS Enactor」进程在一个异常延迟时竞速；第二个 Enactor 应用更新计划并运行 cleanup，而第一个用陈旧的旧计划覆盖区域端点，cleanup 随后删除了该记录。DynamoDB 故障级联到 EC2（DWFM「congestive collapse」）、Network Load Balancer 健康检查抖动，以及 Lambda，约 15 小时。

我的判断：这里的致命组合是**「旧写入者能覆盖新状态」+「清理者不带版本校验」**。冗余本意是容灾，但两个写者没有 fencing token 或版本号，谁晚到谁赢，而清理逻辑又假设「我删的一定是被替换的旧东西」。我要的是单调版本号 + 删除前的 compare-and-swap：旧计划根本不允许覆盖新计划，cleanup 只能删除自己确认过期且未被改写的对象。这和 [[双 leader 双 controller：ZooKeeper 重供给引发的脑裂]] 是同一个病的不同器官——两个写者都以为自己是唯一的。级联放大机制见 [[重试把恢复变成二次灾难：惊群与重试风暴]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例： fencing token 需要中央发放者，若发放者本身是单点，会把竞态问题换成可用性问题——要权衡。
- 边界：读多写少的 DNS 场景适合 CAS；高频写入场景用 CAS 会产生大量冲突重试，反而放大负载（见重试风暴那条）。
- 反例：给 cleanup 加延迟删除（软删除 + TTL）能降低误删风险，但若 TTL 太长，错误记录会持续污染解析，恢复反而更慢。

⭐ 两个写者都以为自己唯一时，冗余就是竞态；删除操作必须带版本校验。
