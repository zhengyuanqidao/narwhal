## 一句话结论

一个 Tokyo AZ 的服务器因冷却失效过热断电，使用 ALB + AWS WAF 或粘性会话的客户即便本身是多 AZ 部署，仍然看到跨 AZ 影响。

## 展开与个人判断

原文事实：第三方数据中心控制系统代码 bug 在 control-host failover 期间造成过量交互，使冷却控制系统无响应。大部分机房正确地把冷却失效切到「最大冷却」模式，但小部分冷却单元反而停机；操作员发起的「purge」模式也失败，因为控制空气处理单元的 PLC 同样无响应。一个 Tokyo AZ 的 EC2 过热断电；使用 ALB + AWS WAF 或粘性会话的客户，尽管是多 AZ，仍出现跨 AZ 影响。

我的判断：多 AZ 只隔离了**计算与存储的位置**，没有隔离**共享控制面**和**有状态的路由语义**。当 WAF/ALB 这类资源或粘性会话把流量绑在某个 AZ 的可用性上，AZ 故障就会沿着这些共享依赖传播。我后来给团队的一条硬规则是：宣称多 AZ 之前，先画出所有跨 AZ 的共享依赖（控制面、全局配置、会话粘性、DNS），凡是画不出来的，就等于没有。全局配置的传播风险见 [[无灰度：一条全局配置变更如何打穿全网]]；电源冗余的失效方式见 [[备份电源在切换瞬间失效：冗余不等于可用]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：不是所有跨 AZ 影响都要消除。粘性会话是业务正确性的取舍，强行改成无状态可能代价更大；关键是**知道**这个取舍存在，而不是以为自己多 AZ 就安全。
- 边界：多 AZ 对无状态、无跨区共享控制面的服务仍然是有效的隔离手段，这条教训只针对共享依赖那一层。
- 反例：把控制面也按 AZ 拆分并不总能带来收益，反而增加一致性难题（参见 [[双 leader 双 controller：ZooKeeper 重供给引发的脑裂]] 那种分裂风险）。

⭐ 多 AZ 隔离的是机器，不是控制面——画出共享依赖之前，别宣称自己高可用。
