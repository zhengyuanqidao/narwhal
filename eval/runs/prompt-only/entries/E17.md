## 一句话结论

恢复信号本身会变成放大器：Discord 一个 flapping 服务恢复时引发惊群重连，前端内部队列填满、内存耗尽；Slack 因大规模断线-重连超出数据库容量，**5%** 用户最长 **2 小时**连不上；Google 的 Service Control 空指针让各区域 crash loop，大区重启时 thundering herd 把 Spanner 压垮，恢复最长 **2h40m**。

## 展开与个人判断

原文事实：Discord 的 flapping 服务恢复时 thundering herd 重连，前端服务因内部队列填满耗尽内存；Slack 大量用户断连后重连过程超出数据库容量，级联连接失败，5% 用户最长 2 小时无法连接。Google 一条含空字段的策略变更触发 Service Control 空指针，失败路径没有 feature flag 保护也缺错误处理，策略全球复制后各区域 crash loop；red-button 修复 40 分钟内部署，但 us-central-1 等大区因重启时的 thundering herd 压垮 Spanner，恢复最长 2h40m。Amazon 一例中元数据服务响应超时导致存储节点下线，下线节点持续重试使元数据负载永远降不下来；另有客户端连接浪涌引发重试与持续拥塞。Spotify 则明确是缺少指数退避引发级联。Launchdarkly 在 AWS 恢复后 SDK 重试冲击流式服务、LB 无响应，美国流式服务又挂了约 12 小时。

我的判断：**重试是正反馈回路**——服务越差、重试越多、服务越差。我要的是三件套：指数退避 + 抖动（jitter）、全局重试预算、以及恢复后的渐进放量（不能让所有客户端同一秒冲回来）。注意 AWS 那例「节点下线后持续重试让负载降不下来」，这正说明优雅降级比快速失败更重要。配置侧的类似放大见 [[最小健康主机数被配置默认值吞掉]]；DynamoDB 级联的底层机制见 [[两个 DNS Enactor 竞态：DynamoDB 空记录与 15 小时级联]]；另一种「容量被悄悄耗尽」的隐蔽形态见 [[20 秒连接等待，24 次部署才抓到的真凶]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：重试预算设得太紧会让短暂抖动变成永久失败——要区分「可重试」与「已尽力」的语义。
- 边界：无状态的幂等读可以激进重试；非幂等写（如扣款）重试必须带幂等键，否则重试变成重复扣款（见 [[一条命令删错库：手误的杀伤半径]] 里 Stripe 类事故）。
- 反例：抖动若用同一种伪随机源（未加种子差异），所有客户端仍会同步重试。

⭐ 恢复不是开关，是一条需要限流的闸门——让所有客户端同时回来的设计，等于没恢复。
