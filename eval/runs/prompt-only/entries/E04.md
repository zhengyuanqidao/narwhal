## 一句话结论

一次部署改了 PostgreSQL 里作业分发服务所用字段的类型：新行用新类型、老行用老类型，严格 schema 校验每次扫描都失败，分发停摆；回滚之后两次部署之间写入的行又变得不可读。

## 展开与个人判断

原文事实：部署改了 PostgreSQL 中 job-distribution 服务某字段的类型；新写入行用新类型、旧行用旧类型，distributor 的严格 schema 校验在每次扫描时失败，停止分发工作。回滚使两次部署之间写入的行不可读，分发继续失败；恢复需要手动部署一个忽略该问题字段的构建，外加人工扩容。

我的判断：这类事故的可怕之处在于**回滚不是逆操作**。大家默认「出问题就回滚」是免费的安全网，但在有状态系统里，回滚只是把代码指针拨回去，数据已经分裂成两个世界。严格校验在这里是帮凶：它让新旧数据无法共存，把「渐进迁移」这条路直接堵死。我后来的做法是类型变更必须走**扩展-收缩**（先接受两种类型、再清理旧类型），并且把「忽略问题字段」这种降级开关预先做进发布包，而不是事到临头手搓一个构建。数据库侧同类教训见 [[迁移最后一步 rename 让只读副本集体死锁]]；配置侧的默认值陷阱见 [[最小健康主机数被配置默认值吞掉]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：扩展-收缩不是免费的。中间态要长期兼容两种类型，代码复杂度上升，若清理旧类型的收尾被无限期拖延，就永久背上双类型债务。
- 边界：纯内存态、无持久化的字段可以随便改类型并回滚，这条教训只适用于有持久化数据且校验严格的路径。
- 反例：降级开关若长期开启会掩盖数据问题。原文中「忽略该字段」是应急手段，不能变成常态，否则坏数据会悄悄积累。

⭐ 有状态系统里回滚不是撤销键——它只把代码拨回去，数据还在两个世界里。
