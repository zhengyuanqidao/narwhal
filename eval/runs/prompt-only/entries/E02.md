## 一句话结论

测试环境看不到、也没有渐进发布的全局配置变更，就是一颗定时炸弹：Cloudflare 一次性禁用内部 WAF 测试工具触发 Lua 异常返回 HTTP 500，另一次自动清理任务误判所有 BYOIP 前缀待删除并将其移除，Google 甚至把 `/` 写进 URL 黑名单让每个 URL 都报警告。

## 展开与个人判断

原文事实：2025-12-05，一个禁用内部 WAF 测试工具的配置变更**没有渐进发布就全局生效**，在代理 rulesets 模块触发 Lua 异常，使用 Cloudflare Managed Ruleset 的客户收到 HTTP 500。2026-02-20，自动清理任务的 bug 错误查询 Addressing API，把**所有 BYOIP 前缀**当成待删除并系统性移除。Google 那条更朴素：`/` 被签入 URL 黑名单，导致每个 URL 都显示警告。

我的判断：三类事故形态不同，根因同一——**变更的作用域大于可观测的作用域**。测试环境的盲点让 2022-10-25 的 Tiered Cache 变更在测试环境没暴露（约 6 小时、峰值约 5% 请求失败、状态码 530）；全局开关没有 canary 让 2025-12-05 的 Lua 异常直接打到所有客户；自动任务没有 dry-run 让 BYOIP 前缀被批量删除。我要的不是「更仔细」，而是**结构性约束**：任何配置变更先落一个 cell/region，确认指标再扩。细节和 [[最小健康主机数被配置默认值吞掉]] 是同一层的防御（一个管语义、一个管爆炸半径），而 [[带外 WAF 变更：不在 Terraform 里就等于没发生]] 说明光有灰度还不够——变更本身可能根本不走你的发布管道。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：不是所有配置都值得做灰度。低风险、可瞬时回滚的展示开关做 canary 是浪费，应把预算留给有状态、有全局传播路径的变更。
- 边界：灰度只在「各 cell 行为同质」时有效。若某 cell 有独特流量签名（原文里 Amazon 那个触发潜伏缺陷的特定包签名），灰度可能恰好跳过真正危险的 cell。
- 反例：灰度 + 自动回滚也可能误伤。若回滚路径本身没被验证（见 [[字段类型改动：回滚让新旧数据互不认识]]），灰度失败后的自动回滚会把你推进更深的坑。

⭐ 作用域大于观测域的变更，不是风险高，是根本不可控——先缩作用域，再谈仔细。
