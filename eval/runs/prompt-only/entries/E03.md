## 一句话结论

一次「自认为是只读排查」的操作改了 AWS WAF，开始拦截 `api.circleci.com` 和 `circleci.com` 的正常流量；因为这次变更没进 Terraform，响应者主动把 WAF 从嫌疑列表里划掉，转去追 CORS 和最近的发布。

## 展开与个人判断

原文事实：IAM 角色缺口允许绕过 CircleCI 的 Terraform 管道对 AWS WAF 做带外变更；一名操作员执行他以为是只读的排查动作时改了 WAF，开始拦截两个 CloudFront 分发的合法流量。由于变更没记录在 Terraform 里，响应者降低 WAF 的嫌疑优先级，去追 CORS 错误和近期部署，直到**自动漂移检测**暴露差异。

我的判断：这是「地图不等于疆域」的典型。IaC 的意义不是方便部署，而是给排障提供一份**可信的变更账本**；一旦账本不全，它在事故中会变成误导——「Terraform 没改」被当成「没人改」。我要的是两件事：一是把 IAM 权限收紧到 WAF 只能经管道写（带外写入直接 denied），二是把漂移检测当成事故时的第一手证据，而不是合规报告里的摆设。这和 [[无灰度：一条全局配置变更如何打穿全网]] 互补：灰度管的是「改动怎么铺开」，IaC 完整性管的是「到底有没有改动」；后者不成立时前者无从谈起。凭据层面的入口问题见 [[凭据与供应链：被窃取的信任链]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：漂移检测只能发现「与账本不一致」，发现不了「账本一开始就错」。初始 import 漏掉的资源会长期「无漂移」地存在。
- 边界：紧急止损时确实需要带外操作（改不动 Terraform 就得先救人），但必须强制留下事后补账的闭环，否则下一次排障又会被残缺账本误导。
- 反例：把只读权限给所有人也不能根除——原文里操作员是「以为自己在只读」，权限缺口才是让误操作生效的条件。

⭐ IaC 账本不全时，它不是证据，是误导；排障第一步先问「有没有带外变更」。
