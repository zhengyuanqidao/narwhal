## 一句话结论

例行 ZooKeeper 重供给时替换主机加得太快，选出了第二个 leader，形成两个独立的 ZooKeeper 集群；后台作业系统的一个 Kafka broker 连上新集群并把自己选为 controller，于是两个 Kafka 集群向客户端提供冲突状态，约 **10%** 的后台作业写入在 **2h32m** 内失败。

## 展开与个人判断

原文事实：在例行 ZooKeeper reprovisioning 中，替换主机添加过快并选举出第二个 leader，造成两个不同的 ZooKeeper 集群。后台作业系统的一个 Kafka broker 连接到新集群并选举自己为 controller，两个 Kafka 集群向客户端提供冲突状态；约 10% 的后台作业写入在 2h32m 中失败。同章节 GitHub 另一例：43 秒网络分区触发 MySQL 主库 failover，新主因跨洲延迟缺少数秒写入，花了 24+ 小时做数据完整性恢复。

我的判断：** Membership 变更是分布式系统最危险的时刻**，因为「谁是权威」在那一刻没有共识。替换节点太快的本质是并发加入没有 barrier——旧集群还没确认收敛，新节点已经能投票。我要的是显式 membership 协议：一次只加一个节点、等 quorum 稳定后再加下一个，并且所有客户端连接串带同一份版本标识，避免连到「另一个集群」。同章的 43 秒分区说明另一面：网络抖动 + 跨洲延迟会让 failover 丢写，比脑裂更难发现。主备提升还会改变 ID 语义，见 [[序列号的 32 跳变：HA 提升后的 ID 断层]]。双写者竞态见 [[两个 DNS Enactor 竞态：DynamoDB 空记录与 15 小时级联]]；迁移过程中的副本状态问题见 [[迁移最后一步 rename 让只读副本集体死锁]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：一次只加一个节点会拖慢大规模扩容，别在稳态扩容时套用；这条纪律只针对 leader/quorum 变更窗口。
- 边界：若系统有强 fencing（如 STONITH），双 leader 会被自动解决，但 GitHub 同章另一例里 STONITH 反而把 passive 节点全关掉，说明 fencing 自身也需要边界。
- 反例：让客户端「自动发现」leader 在分裂时会把流量送到错误集群；静态配置虽笨，分裂时反而更安全。

⭐ 成员变更是分布式系统最危险的瞬间——权威未定的时候，加节点就是加一个王。
