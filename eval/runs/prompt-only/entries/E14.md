## 一句话结论

整数天花板不会提前打招呼：GitHub 的 scoped-tokens 表外键撞上 max INT32，Actions 与 Pages 高失败率、scoped-token Git 操作中断 **9h48m**；Heroku 的外键用了比主键更小的数据类型，主键溢出后无法新建授权，值班操作又触发 API 全面中断。

## 展开与个人判断

原文事实：GitHub 中 scoped-tokens 表的一个外键达到 max INT32，导致 Actions 和 Pages 高失败率，scoped-token Git 操作中断 9h48m；缓解需要一次长期运行的 schema 迁移到 INT64。能在建列前就发现问题的数据检查（linting）比该列本身出现得还晚。一次 Action 短暂收到未授权访问授权后被撤销。同章节另一起事故里，低效的 GitHub App 权限 API 端点加上超时重试调用方，在 auth-token 集群造成 **7×** 写延迟尖峰、峰值 **76%** 的 token 签发失败。Heroku 在 2023-06-08 15:05 UTC 发生数据库错误：外键数据类型小于其引用的主键，主键超出允许值时溢出，无法创建新授权、客户无法新建部署，oncall 操作随后触发 Heroku API 全面中断。

我的判断：这是**类型选择与增长预测脱节**的慢性病。INT32 上限约 21 亿，在低频表上像天文数字，在高频 token/授权表上只是时间问题。我要的是：主键/外键统一用 BIGINT 起步（成本远低于事后迁移），并且把「自增列剩余空间」纳入容量看板——它和磁盘、连接池一样是会耗尽的资源。另一个警示是 GitHub 那次「linting 比列本身还晚出现」：防护机制追不上基础设施的演化。类型不兼容的连带坑见 [[字段类型改动：回滚让新旧数据互不认识]]；大表迁移本身的风险见 [[迁移最后一步 rename 让只读副本集体死锁]]。

事实来自公开复盘，判断为本次提炼，未经用户复核。

## 适用边界/反例

- 反例：全表无脑改 BIGINT 会增加索引体积与内存占用，在超大规模表上不免费；但比起 9h48m 的中断，这笔成本通常值得。
- 边界：低增长、有明确上限的配置表用 INT32 没问题，别为了「统一」而迁移。
- 反例：光改列类型不改应用端的整数解析（如 JS 的 Number 精度）会把溢出问题搬到客户端。

⭐ 自增主键是会被耗尽的容量资源——把它放进看板，别等它自己说话。
