# Narwhal 零脚本版 — 一句话，把文档变成知识库

> 这是「文档变知识库」的**零脚本变体**：不调用任何 Python 脚本，全部由助手按本文件直接完成。
> 适合本机没有 Python、或使用不支持脚本执行的环境。能力与带脚本版对齐，执行方式不同（见 §零）。

## §零 给使用者：你只需要一句话

**不用安装任何东西，不用懂技术，不用建目录，不用回答问题。** 把你的文档放进一个文件夹，然后说：

> **「把这个文件夹变成知识库」**

助手会自动完成：扫描 → 分诊 → 建领域 → 写条目 → 建地图 → 体检 → 出成品。
中途**不会问你问题**（除非你主动说"我要自己定领域"）。你会在工作区得到一个 `wiki/` 目录和一份可转发的成品说明。

想更具体，也可以这样说（都不需要技术操作）：
- 「把这份复盘变成一条能照做的经验」→ 只处理这一个文件
- 「检查我的知识库哪里太空洞」→ 体检现有库
- 「把这个库导出一份能给别人看的说明」→ 生成可转发成品

## §一 与带脚本版的能力对照（诚实说明差异）

本版把脚本做的事分成三类，处理方式不同：

| 脚本做的事 | 本版怎么做 | 是否等价 |
|---|---|---|
| 分诊、聚类、写条目、建 MOC、交叉引用（模式 B/E） | 本就是助手的推理活，**完全照做** | ✅ 等价 |
| doctor 断链/孤儿/元数据检查 | 助手逐条推理核对（§模式 D） | ✅ 等价（规则判断） |
| report 溯源率、反例密度、重复、覆盖 | 助手语义核对 + 定性判定（§模式 D） | ⚠️ 判断等价，**不给假精确百分比** |
| report 的 MinHash 精确重复率、字符级覆盖率 | 助手改做"语义重复/整章漏料"判断 | ⚠️ 从精确数字降级为定性结论 |
| export 的 human/rag 双格式、反例段独立 chunk | 助手按 §模式 F 直接生成文本 | ✅ 等价（格式化） |
| wiki_version 的三级指纹/相似度 | 助手用 §版本管理 的简化规则 | ⚠️ 简化版，不做逐字指纹 |

> **诚实边界**：凡涉及"精确百分比/哈希指纹"的，本版给**定性结论 + 具体证据**（如"第 3、5 章未覆盖""条目 X 的数字 ¥99 在原文找不到"），不编造一个看起来精确的数字。要可签字的精确报告，请用带脚本版。

## 核心理念

1. **经验 > 信息**：只沉淀"我经历过、验证过、有独家判断"的内容，不搬运通用知识。
2. **条目原子化**：一个条目讲透一个知识点/方法/教训，500~1500 字。
3. **互联成网**：条目之间必须双向链接，孤岛条目是失败的知识库。
4. **地图优先**：先建 MOC（Map of Content），再填条目；没有地图的知识库会失序。
5. **编译而非检索**（Karpathy llm-wiki 模式）：知识编译一次、持续维护，而非每次查询临时检索；源材料不可变，条目由助手拥有并维护。
6. **默认无人值守**：助手自主判定、自动分批，不要求用户在场逐条确认。所有"提交用户确认"改为**可选**（用户明确要求交互时才等），默认自主判定并在产物中留痕待复核。

## 领域知识库与技能输出

### 按领域组织

一个 wiki 可含多个领域（domain），每个领域是独立子知识库：

```
wiki/entries/<领域>/   wiki/cases/<领域>/   wiki/moc/<领域>.md
```

领域由发现阶段自动聚类（见模式 E），默认自主选定（宁少勿多，允许 1 个），留痕待复核。领域数量 1~7 个。

### 领域工作技能输出（skill-forge）

某领域积累到 ≥5 条目 + ≥2 案例后，可按指令把该领域编译为可交付工作技能，写到 `wiki/exports/<领域>/`：

1. `SOP.md` — 标准作业流程，步骤化可执行
2. `CHECKLIST.md` — 开工前检查清单，从 pitfall 条目反推
3. `PLAYBOOK.md` — 实战手册，按场景索引的复盘
4. `BRIEF.md` — 领域简报：专家主张、能力边界、可承接任务
5. `skill.md`（可选）— 压缩为 Agent Skill 格式

输出原则：只引用 wiki 内已验证内容，confidence 低的条目不进 SOP/CHECKLIST；每份注明来源条目。

## 知识库目录结构（三层架构）

知识库根目录默认为 `<工作区>/wiki/`（用户指定则从其指定）。用文件工具创建下列结构：

```
wiki/
├── SCHEMA.md            # 约定：目录规则、条目模板引用、标签、领域配置
├── HOME.md              # 内容目录 + 每条一句话摘要 + 最近更新
├── log.md               # 追加式动作日志（YYYY-MM-DD | 模式X | 动作），只增不删
├── triage.md            # 分诊记录（每文件标签 + 混合文档拆分 + 待复核留痕）
├── raw/                 # 第1层：不可变源材料，原样归档
├── moc/                 # 第2层：知识地图，一域一图
├── entries/             # 第2层：原子条目（助手拥有）
├── cases/               # 第2层：经验案例
├── methods/             # 第2层：方法论/SOP/检查清单
├── profile/
│   ├── EXPERT-PROFILE.md
│   └── OPEN-QUESTIONS.md
├── exports/<领域>/      # 领域技能输出物
└── dist/                # 交付成品（human/ rag/ SHARE.md index.html）
```

规则：
- `raw/` 一经写入**永不修改**；助手只读取，提炼落到 entries/cases。
- 条目引用源材料用相对链接指向 `raw/`。
- 每次写操作（新建/更新/体检）结束，**在 log.md 末尾追加一行**：`- YYYY-MM-DD | 模式X | 动作摘要`。

## 会话恢复仪式（orientation，每次必须先做）

面对已有 wiki，做任何 ingest/query/lint 前，依次：
1. 读 `SCHEMA.md` — 领域配置与约定
2. 读 `HOME.md` — 已有条目及摘要，避免重复/漏链
3. 读 `log.md` 最后 20~30 行 — 最近做过什么
4. 条目超过 100 篇时，先按关键词搜索再决定新建还是更新

## 条目模板（assets/templates/entry.md）

必填字段（YAML frontmatter）：

```yaml
---
title: 条目标题
domain: 所属领域
type: concept | method | pitfall | insight | resource
confidence: 高 | 中 | 低 | 低·外部参考
source: 经验来源（项目/事件/阅读）
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
links: ["[[相关条目]]"]
---
```

正文固定三段：**一句话结论 → 展开与个人判断 → 适用边界/反例**。
（§模式 D 的反例密度指标依赖第三段，不可省略。）

## 案例模板（assets/templates/case.md）

**背景 → 我做了什么 → 结果 → 复盘（学到什么/下次怎么做）→ 关联条目**。

## 版本管理（简化版，无脚本）

- 每次交付，在 `wiki/VERSION` 写版本号，`CHANGELOG.md` 追加一行"本次比上次好在哪"。
- 版本规则：`patch`＝文字修订；`minor`＝新增条目/领域；`major`＝目录或约定变更。
- **存量不重跑**：只处理新增/修改/删除部分。源材料小改（如一个数字）只改对应条目，不重跑整条。
- `raw/` 不可变：源材料更新时登记为新文件（如 `xxx.v2.md`），条目 `source` 指向新版。
- 条目被人改过：保留人的改动，不覆盖。
- （与带脚本版的差异：本版不做 sha256/MinHash 逐字指纹，靠助手判断变更幅度。）

## 工作流

### 模式 A：初始化（cold start）

用户第一次建库或想从零规划：
1. 从素材（无素材则用访谈提问）提炼 3~5 个领域，每域列 5~10 个候选条目与案例。默认自主定，不等确认。
2. 创建完整目录结构（含 SCHEMA.md、log.md、triage.md、raw/），领域配置写入 SCHEMA.md。
3. 已有素材原样归档进 `raw/`，再提炼第一批条目（每域至少 1 条，宁缺毋滥；无真实经验的领域标"待验证"）。
4. log.md 记录初始化动作。

### 模式 B：深潜（ingest）

用户丢来经历/对话/文档，或说"把这个沉淀下来"：
0. 先执行 orientation。
1. **归档源材料**：原文原样存入 `raw/<YYYY-MM-DD>-<来源名>.md`，永不修改。
2. **提炼**：识别知识点、方法、踩坑、结论，自主判断哪些值得入库（避噪音），在 triage.md 留痕"未经用户复核"。默认不等待确认。
3. **入库**：按模板写条目/案例，回链 raw；与现有条目交叉比对——有则更新，无则新建并链接相邻条目。
4. **更新地图**：新条目挂进对应 MOC；新领域则新建 MOC 并更新 HOME.md。
5. **更新画像**：能力提升或新增代表作时更新 EXPERT-PROFILE.md。
6. **反哺问题**：空白与疑问写入 OPEN-QUESTIONS.md。
7. **记日志**：log.md 追加一行。

### 模式 C：导航（query）

用户问"我关于 X 积累了什么"：
0. 先执行 orientation。
1. 从 HOME.md 或 moc/ 找地图 → 顺链接读条目 → 以"条目引用 + 个人判断原文"方式回答。
2. 库中无相关内容则如实回答，并建议是否沉淀入库。

### 模式 D：体检（lint）— 用推理替代脚本

用户说"体检/检查知识库"，或每次大额入库后主动建议。**逐项做，把结果写成 `wiki/验收报告.md`**：

1. **断链检查**：扫描所有条目正文里的 `[[双链]]`，逐个确认指向的标题在 `entries/` 中存在。列出所有指向不存在条目的断链。
2. **孤儿检查**：统计没有任何入链（不被 HOME/MOC/其他条目链接）且自身无出链的条目。列出清单。
3. **元数据检查**：每条是否有 title/domain/type/confidence/source/created/updated；正文是否有三段（尤其"适用边界/反例"）。
4. **五项内容层指标**（定性判定，给证据，不编造精确百分比）：
   - **覆盖率**：列出 `raw/` 源文档的所有二级标题（排除"目录/致谢/参考/附录"等结构性章节），逐个判断"有无条目覆盖其**实质内容**"。列出未覆盖章节。**判据：不得有整章漏料。**
   - **溯源率**：抽查条目中的每个数字（¥X、X元、X%、X 家等）和关键专名，在源文档里找对应。**列证据**："条目 X 的 ¥99 在原文找不到"＝编造，必须删或改。判据：不允许无来源的数字。
   - **孤儿率**：同第 2 项，用"无入链条目数 / 总条目数"给定性结论（如"12 条中 1 条孤立"）。
   - **重复率**：语义判断同领域条目是否"讲同一件事"（不是字面重复，是结论重复）。列出疑似重复对。
   - **反例密度**：统计含"适用边界/反例"段的条目占比。列缺失的条目。
5. **交付判据**：覆盖率无整章漏料 + 溯源无编造 + 孤儿≤20% + 无明显重复 + 反例密度≥80%。**不达标先修再交**，报告显式列出未覆盖章节，不许只说"全部达标"。
6. **矛盾检测**：同领域两条结论冲突时，在两条中互相标注 `> ⚠️ 与 [[对方]] 存在矛盾：……`，留给用户裁决。
7. 体检结果与修复动作记入 log.md。

### 模式 E：全域扫描（discover）— 建库主入口

用户说"把这个文件夹变成知识库/扫描我的资料/自动发现"时：

**1. 采集**（按顺序，找到什么读什么）：
- 本地：用户指定目录、`/root/uploads/`、`/workspace/`。
- 云端：项目网盘/云文档只读——不修改云端文件，需沉淀的拷贝进 `raw/`。
- 支持 md/txt/docx/pdf/xlsx/pptx/csv 等；二进制用对应工具解析为文本。

**2. 分诊**（每份文件快速打标，不精读）：
- `经验` — 我做过的事（复盘、总结、周报、方案、会议纪要）→ 优先入库
- `参考` — 别人的知识/行业资料 → 只挑少数相关条目，标 `confidence: 低·外部参考`
- `噪音` — 无关文件 → 跳过，报告扫描统计（读了 N、经验 X、参考 Y、跳过 Z）

**混合文档拆分**（一份同时含外部情报与我方决策）：
- 按段落/章节拆：外部事实归 `参考`（标 `低·外部参考` + 来源），我方判断归 `经验`（正常 confidence）。
- triage.md 用两行记录同一文件、标签不同，各注取了哪些段落；`raw/` 仍只存一份原样副本。
- 判据：含"我/我们"第一人称决策或"据此我改成/我决定"＝经验；纯转述他人事实＝参考。

**3. 聚类分域**：按主题聚类（依据文件名、关键词、业务对象、反复场景），自主选定领域（宁少勿多，允许 1 个），triage.md 写明"领域为自动判定，待复核"，列为统计报告第一条待办。**禁止伪装成"已获用户确认"。**

**4. 批量入库**：按选定领域走模式 B 逐文件深潜（每域先出 MOC 和高价值条目），自动分批续跑，批次间不等人工汇报。

**5. 更新** SCHEMA.md 领域配置表与 log.md。

纪律：
- 单次扫描最多精读 20 份；超出的**自动按批次续跑**（按文件名/修改时间稳定排序），不列清单让人排优先级。每批进度写 log.md，全部跑完再给统计报告。
- **交互模式（可选）**：仅当用户明确说"我要自己定领域/每批给我看"时才等确认；默认不等。
- 结束必须给统计报告：来源分布、领域结果、入库数量、下一个深潜主题。

### 模式 F：交付导出（export）— 用文本生成替代脚本

用户说"导出/给别人看/一键出成品/交付"时：

**0. 默认一键收尾（无需在场）**：直接依次做下面 1~5 步，一次跑完，不 intermediates 等确认。

**1. 先按模式 D 验收，不达标不导出**：断链、孤儿、元数据、五项指标。不达标先修。

**2. 人读版 `wiki/dist/human/`**：把每个条目原样输出为 markdown（保留 frontmatter、⭐ 结尾、双链），按领域分目录。

**3. RAG 入库版 `wiki/dist/rag/`**：把每个条目按 `##` 小节切成 chunk，每 chunk 开头加元数据行：
```
[title] 条目标题
[section] 小节名
[domain] 领域
[type] 类型
[confidence] 确信度
[source] 来源
```
文件名 `<条目名>/序号.txt`。**关键：正文里的"适用边界/反例"段必须单独成一个 chunk**——否则检索"这方案有什么风险"时边界条件会被正文淹没。每 chunk 控制在约 500 字以内，超长就再切。

**4. 按 scope 分开（可选）**：条目 frontmatter 有 `scope`/`owner` 时，按 scope 分目录导出，无 scope 的进 `_shared/`。**只做标签与切分，不做运行时鉴权**（鉴权属系统层）。

**5. 传播节点（本版重点，替代 run.py 的 SHARE 生成）**：在 `wiki/dist/` 生成两份可转发文件——
   - `SHARE.md`：标题 + "N 条可复用判断" + 6 条以内「标题—一句话结论」节选 + 质量说明（内容层判据，注明"命中率/响应属系统层不覆盖"）+ "我自己也想要一份，怎么做"（一句话触发说明）+ 落款与日期。
   - `index.html`：同样内容的单页静态网页，纯 HTML 内联样式，无外部依赖，可直接在浏览器打开转发。
   - 两里的"技能地址"若未上架，写占位符 `{上架后替换为技能市场链接；未上架时保留本行，不要删}`，**不许编造 URL**。

**6. 清单**：在 `wiki/dist/` 写 `MANIFEST.json`（生成时间、版本、条目数、验收结论、五项判定、产出清单、链接占位符）。

完成标志：用户拿到一个 `wiki/dist/` 目录，里面 `human/`、`rag/`、`SHARE.md`、`index.html`、`MANIFEST.json` 齐全，可以直接转发或交付。

## 质量红线

- 未经用户确认的经验标 `confidence: 中`（我方决策）或 `低·外部参考`（外部资料），注明"未经用户复核"；默认无人值守下这不算违规，但必须留痕。
- `raw/` 不可变；log.md 只追加；SCHEMA.md 是唯一结构权威。
- 不搬运网上随处可见的通用知识；通用背景最多一句带过并给链接。
- 新条目必须至少链接 1 个已有条目；**例外**：首次建库中无已有条目时，要求每条被 HOME.md 或 MOC 挂载，并在同批条目间交叉引用；第二批起恢复原要求。
- **双链写法（体检判据，必须遵守）**：`[[双链]]` 必须写在**条目正文里**——frontmatter 的 `links:` 字段不算（体检只解析正文的 `[[...]]`）；链接目标必须是**目标条目的 `title` 字段原文**，不是文件名、不是领域名。MOC 的"与其他领域的关系"若指领域，写**普通文本**不要加 `[[]]`；只有指向具体条目时才用 `[[条目标题]]`。违反会被体检判为"断链"和"孤儿条目"（已由本版换手实测复现：仅写 links 字段 + 用领域名当链接 = 24 断链、孤儿 100%）。
- 每次更新 HOME.md 的"最近更新"区块。
- 每次交付更新 VERSION 与 CHANGELOG.md——用户要能回答"这次比上次好在哪"。
- 不因一次微改重跑整条：判断变更幅度，小改只改局部。
- **不编造精确数字**：无法可靠计算的比例，用定性结论 + 具体证据，不写一个看起来精确的百分比。

## 写作风格

第一人称专家视角，直接、有立场（"我后来改成 X，因为 Y"），拒绝百科腔。条目结尾用一行"⭐ 一句话给三年后的自己"。
