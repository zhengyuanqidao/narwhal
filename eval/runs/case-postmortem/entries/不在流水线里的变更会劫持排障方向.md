# 不在流水线里的变更会劫持排障方向

**一句话结论**：排障的第一动作永远是"最近改了什么"，所以只要有一类变更不在记录里，它就会被系统性地排除在嫌疑之外。

## 展开

CircleCI 2025 年 4 月的事故是这条最好的教材。一个 IAM 角色的权限缺口，允许有人在 Terraform 流水线之外直接改 AWS WAF。一位工程师在做他以为只读的排查动作时改了 WAF，开始拦截到达 `api.circleci.com` 和 `circleci.com` 的正常流量。因为这次变更没有记录在 Terraform 里，响应者把 WAF 从嫌疑名单里降权，转去追 CORS 报错和最近的部署——直到自动化的漂移检测（drift detection）把差异翻出来，才找到真凶。

这里的关键不是"有人违规改了配置"，而是**排障逻辑被污染了**：所有人的推理都建立在"变更清单是完整的"这个前提上，前提不成立，推理越严谨越走偏。

## 适用边界 / 反例

反例是"我们所有变更都走流水线"这种自信——只要存在一个带管理权限的人、一个控制台、一个应急通道，这个前提就不成立。可行的边界做法：把"变更清单不完整"当成默认假设，在排障时先花五分钟问"有没有人用控制台改过任何东西"，并让漂移检测常态化。适用场景是所有有多人、多入口的云环境；纯单人环境这条的收益会低很多。

⭐ 一句话给三年后的自己：排障不是找答案，是先验证你手上的"已知条件"是不是真的。
