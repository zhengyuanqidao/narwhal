# 配置没有语义校验就等于没有测试

**一句话结论**：配置错误（Config Errors）里最致命的不是写错字，是"写了一个语法合法、语义危险的键"——系统不会报错，只会安静地回退到默认值。

## 展开

Amazon 首尔区域的一次配置变更，删掉了"EC2 DNS 解析器集群最少健康主机数"这一项设置。语法完全合法，但删除后系统回退到一个极低的默认值，健康主机数一路掉，VPC 内 DNS 查询失败约 84 分钟，最后靠人工恢复容量。AWS 的补救措施很有指向性：加语义校验（semantic config validation），并对主机移除做每小时限流。这说明他们认的问题不是"有人手滑"，而是"系统允许一次变更把安全边界悄悄调低"。

另一类是"没有灰度"。Cloudflare 2025 年 12 月一次变更，为了关掉内部 WAF 测试工具，直接全局传播而没有渐进式发布，触发代理规则模块的 Lua 异常，用 Cloudflare 托管规则集的客户全部收到 HTTP 500。更早还有一次路由器规则配错，导致所有边缘路由器崩溃。

三类危险配置值得单独标记：**删除一个键（回退默认值）、把限值调低、把开关关掉**。它们的共同点是"变小"，而监控通常只对"变大"报警。

## 适用边界 / 反例

反例是把"配置上线前 review 过"当成保障——review 抓的是显式错误，抓不到"删除后默认值是多少"。可行的边界：给关键配置项写"缺失时的行为"测试，而不只是"值正确"的测试；任何影响安全边界的配置变更，必须走灰度。这条对单体小系统收益有限，对多区域、多租户系统是刚需。

⭐ 一句话给三年后的自己：问"这个键删了会怎样"，比问"这个值对不对"更能救命。
