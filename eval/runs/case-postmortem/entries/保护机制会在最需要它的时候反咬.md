# 保护机制会在最需要它的时候反咬

**一句话结论**：限流、退避、超时这些机制是按"正常故障"设计的假设；当故障规模超出假设，它们会从保护变成放大器。

## 展开

CircleCI 有一次队列雪崩，过程中出现了堪称教科书的反向行为：build-scheduler 的失败模式限流器（failure-mode throttles）在"其实是正常条件"下被触发，而且在最需要吞吐的时候主动退避（backed off precisely when more throughput was needed）。保护机制用的判据是"重试变多了，说明后端有问题"，但当问题本身是队列积压时，重试变多恰恰是恢复的表现。

GitHub 的另一种反咬更隐蔽：systemd 把一个进程的 `LimitNOFILE` 从 1,073,741,824 悄悄压到 65,536，因为内核级上限是 1,048,576。没有报错、没有告警，只是连接数不够用了。这个案例的价值在于——**保护机制可能来自操作系统，而不是你的代码**，你读自己的配置文件永远看不到它。

第三类是"排查动作本身触发故障"：GitHub 为了排查性能问题打开内存 profiling，结果又触发一次连接失败，需要再一次主库切换。

## 适用边界 / 反例

反例是把"我们有限流"当成熟度标志——限流只有在"判据能区分真故障与恢复期"时才有效。可行的边界：给每个保护机制写一条"它在什么情况下判断会错"，并保证这个判断错了也不会阻塞恢复路径（比如提供人工强制放行开关）。这条对所有自动伸缩、自动熔断、自动重试系统都适用；对纯静态服务不适用。

⭐ 一句话给三年后的自己：保护机制的错误方向，永远指向"更保守"，而故障恢复需要的恰恰是"更激进"。
