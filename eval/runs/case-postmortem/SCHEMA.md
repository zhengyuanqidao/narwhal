# SCHEMA — 本库的建库规则

## 领域划分

本库只有一个领域：**故障复盘**。不分二级领域，因为 8 条条目共享同一套失效机制词汇，强行拆分（如"数据库故障""网络故障"）会让同一条经验被切到两处。

## 条目类型约定

| type | 用途 | 本库占比 |
|---|---|---|
| `pitfall` | 会让人踩坑的机制 | 5 |
| `insight` | 对系统行为的判断 | 3 |
| `method` | 可执行的步骤 | 0（源文档是复盘而非方法论） |

## confidence 判定标准

- **高**：源文档中有 ≥2 个独立案例指向同一机制，且机制描述与案例因果一致
- **中**：仅 1 个案例，或机制需要一定推断
- **低 / 低·外部参考**：来自源文档引用的外部文章，未在本库内交叉验证

## 命名规则

- 文件名 = title，**不缩写、不用编号**（编号会随增删失效，且无法从文件名看出内容）
- 标题写成**一句有立场的判断**，不写成名词短语（"回滚本身也是一次变更" 优于 "回滚风险"）

## 链接规则

- 每条至少链接 1 条其他条目，链接理由必须能在正文里看出来
- MOC 是本库唯一入口，新条目必须挂进 MOC 的某个机制分类下

## 什么不进这个库

- 单一公司的组织性失误（如"某人违规操作"）——不可迁移
- 纯时间线叙述（"X 点发生 A，Y 点发生 B"）——没有判断
- 已修复且不再可能复现的具体 bug（如某版本某函数的空指针）
