# Narwhal Eval —— 评测集与判分口径

> 目的：把「Narwhal 跑得好不好」从主观感受变成**可重复、可回归的数字**。改了 SKILL.md 之后先跑一遍 eval，再决定是否发版。

## 为什么需要它

Narwhal 的产物是 Markdown 知识库，没有测试就没法判断"这版提示词是不是改坏了"。当前 10 项机械检查覆盖的是**结构纪律**（分诊、raw 不可变、元数据、链接、日志、门槛），不覆盖"文笔好不好"——后者留给 agent 判分（见下）。

## 目录

```
eval/
├── golden.json          # 金标准：分诊标签、期望领域、阈值
├── run_eval.py          # 机械判分器（10 项检查，输出 score 与逐项明细）
├── fixtures/
│   ├── archive/         # 12 份模拟散落文档（6 经验 / 3 参考 / 1 噪音 + 2 真实噪音）
│   └── inject/          # 故意做坏的条目，用于体检（case-04）
├── cases/               # 8 个评测用例定义（输入 / 期望 / 判分）
├── RESULTS.md           # 最近一次实测结果（基线 + 反例对照）
└── runs/<case>/wiki/    # 评测产物：已提交 case-01（基线）与 case-04（反例）
```

## 怎么跑

```bash
# 全流程：把某个 case 的产物判分
python3 eval/run_eval.py eval/runs/case-01/wiki

# 只看机器可读结果
python3 eval/run_eval.py eval/runs/case-01/wiki --json

# 退出码：0 通过 / 1 未通过 / 2 用法错误（可直接接 CI）
```

## 判分口径

**机械判分（10 项，脚本自动）**

| # | 检查 | 判据 | 依据的 SKILL 条款 |
|---|---|---|---|
| 1 | 必需产物齐全 | `SCHEMA.md` `HOME.md` `log.md` `triage.md` 都存在 | 目录结构 + 模式 E |
| 2 | 分诊准确率 | 与 `golden.json` 标签一致率 ≥ 90%（边界样本允许二选） | 模式 E 第 2 步 |
| 3 | raw 原样归档 | 每份经验素材的 raw 副本 sha256 与源文件**完全一致** | "raw 一经写入永不修改" |
| 4 | 噪音未入库 | 装修清单、nvm/oh-my-zsh README 不出现在 `raw/` | 分诊"噪音→跳过" |
| 5 | 条目合规 | frontmatter 必填 6 字段齐全、type/confidence 取值合法、正文 ≥200 字、至少 1 条 `[[链接]]`、条目数 6~14 | 条目模板 + 质量红线 |
| 6 | 体检 0 问题 | `wiki_tool.py doctor` 报告问题数 = 0 | 模式 D |
| 7 | MOC 覆盖 | 每个领域有 MOC，且该领域全部条目都被 MOC 链接 | "所有条目必须挂进某张地图" |
| 8 | HOME 索引完整 | 所有条目 title 出现在 `HOME.md`，且有"最近更新"区块 | 质量红线 |
| 9 | log 格式合规 | 每行匹配 `- YYYY-MM-DD \| 模式[ABCDE] \| 摘要` | "log.md 只追加" |
| 10 | 技能输出门槛 | 达不到"≥5 条目 + ≥2 案例"时必须拒绝编译 | skill-forge |

**agent 判分（人工/模型评审，机械检查测不出来的部分）**——每个 case 文件里写明"评审要点"，例如：
- 导航回答是否**引用条目原文**、而不是自己重新编一段；
- 库中没有答案时是否**如实说没有**而不是编造；
- 矛盾检测是否能指出两条互相冲突的条目并请用户裁决。

## `triage.md` 是 eval 新增的产物

现有 SKILL 的分诊只发生在对话里，无法回溯。评测要求产物落一份 `wiki/triage.md`：

```markdown
| 文件 | 分诊 | 理由 |
|---|---|---|
| 2025-08-选品复盘-宠物饮水机.md | 经验 | 我自己算过的到仓成本 |
```

**建议纳入 v1.1**：模式 E 第 5 步增加"写 triage.md"，这样分诊可审计、可回归、也方便用户事后纠错。

## Case 一览

| Case | 测什么 | 输入 | 主要判分 |
|---|---|---|---|
| case-01 | 模式 E 冷启动全流程 | `fixtures/archive` 12 份 + 2 份真实噪音 | 机械 1~10 全部 |
| case-02 | 模式 B 单份深潜 + 查重 | 1 份新复盘（与已有条目重叠） | 是否更新旧条目而非重复建页 |
| case-03 | 模式 C 导航 | 已有库 + 库中没有的问题 | 引用原文 / 不编造 |
| case-04 | 模式 D 体检 | `fixtures/inject` 坏数据 | doctor 应报 4 类问题 + 矛盾检测 |
| case-05 | skill-forge 门槛 | 条目不足的库 | 必须拒绝并说明差多少 |
| case-06 | 质量红线 | 纯通用知识文档 | 不得以 `confidence: 高` 入库 |
| case-07 | raw 不可变 | 改写已有 raw 的指令 | 必须拒绝改写 |
| case-08 | 会话恢复仪式 | 已有库 + 冷启动 | 是否先读 SCHEMA/HOME/log |

## 当前状态（2026-11-10）

| 运行 | 命令 | 结果 |
|---|---|---|
| case-01 基线（模式 E 全流程） | `run_eval.py eval/runs/case-01/wiki` | **100%** / 10 项全 PASS / exit 0 |
| case-04 反例（注入坏数据） | `run_eval.py eval/runs/case-04/wiki` | **60%** / 4 项 FAIL / exit 1 |

两个数字合起来才有意义：基线 100% 说明阈值没定得过严，反例 60% 说明检查项真能抓到坏产物（注入的 4 个病灶被 doctor 4/4 命中）。

细节与未覆盖项见 `RESULTS.md`，其中也写了两个由此暴露的 SKILL 缺口。**建议把 score ≥90% 作为发版门槛。**
