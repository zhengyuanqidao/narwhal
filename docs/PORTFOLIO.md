# Narwhal / WorkBuddy 产品矩阵与运营路线（v0.1）
> ⚠️ 平台事实以 [PLATFORM-AUDIT.md](../../workbuddy-assets/docs/PLATFORM-AUDIT.md) 为准（2026-11-12 系统核查）：**价格可改（每年限 N 次）**，锁死的只是付费方式；收费资格要求已有 1 个过审资产。本文旧结论已修订。
> ⚠️ **路线以 [ROADMAP.md](../../workbuddy-assets/docs/ROADMAP.md) 为准**（2026-11-12 重置，决策门驱动）：本文§三 四波 W1–W4 与 §八 本周动作已作废，降级为历史参考。

> 目标：以公司主体在 WorkBuddy 上构建「**1 个免费流量池 + 3 条付费产品线**」的资产矩阵，并把上架流程本身做成工程。
> 本文承接 `GO-TO-MARKET.md`（单资产打法）与 `POSITIONING.md`（品类定位），回答"接下来发什么、怎么发、怎么运营"。

## 一、矩阵设计原则（四条，均由已核实事实推出）

| # | 原则 | 依据 |
|---|---|---|
| 1 | **卖"别人愿意付钱的那个瞬间"，不卖"我擅长的东西"** | CSDN 拆解文："竞争优势不在技术深度，而在场景窄度 + 经验颗粒度" |
| 2 | **专家卖判断，技能卖省时间** | 官方定义：Skill=工具能力，专家=能力+经验。判断力贵，省时间便宜 |
| 3 | **免费资产养使用量，付费资产收钱** | 牧天打法（约 60 个免费 Skill 引流 + 付费完整工作流）；推荐位按使用热度分配 |
| 4 | **付费方式一次想死，价格可改** | 免费↔付费、买断↔订阅发布后不可改（文档 §3.1 + 控制台 UI）；**价格数值可改**（每年限 N 次、仅管理员、1/1 重置） |

**红线：同时运营的资产 ≤6 个。** 每个资产都要回评价、处理退款、迭代版本，矩阵摊太大等于每个都做不好；使用量马太效应下，6 个好资产 > 20 个僵尸资产。

### 矩阵内部飞轮

```
免费技能铺量 ──使用量背书──▶ 付费专家成交
     ▲                          │
     │              对话内自然引导（agent 正文写死）
     │                          ▼
narwhal 技术底座 ◀──增量编译── 线1 知识库 ←─ B端线索 → 对公交付（利润）
```

三条线不互相蚕食：线 1 卖给"有经验的人"，线 2 卖给"做技术的人"，线 3 卖给"想赚钱的人"——三个人群，同一批资产复用同一套底座。

## 四、运营规划（矩阵层面五件事）

**① 品牌一致性（W1 一次性做完）**
卡片公开显示开发者信息——公司名 + 统一头像风格（512×512 插画，同一色系/构图语言）+ 统一命名格式（「XX官/XX师」）。让用户在市场里刷到第二个资产时认得出：这是同一个团队的。

**② 搜索覆盖（每个资产上架当天）**
免费小技能的 description 各覆盖不同关键词（转 PDF / 纪要 / 周报 / 对账…），付费专家的 tags 按买家人搜（知识管理/经验萃取/SOP；RAG/检索/选型；副业/一人公司/定价）。**三个线的关键词不许重叠。**

**③ 内容飞轮（每周 1 篇，成本部分可回收）**
每发一个资产 → 腾讯云开发者社区发教程（单篇积分上限 3000，换代金券/算力）→ 站外（即刻/V2EX/公众号）发前后对比结果帖。教程标题写"怎么把 XX 变成能用的 XX"，不写"我做了个资产"。

**④ 数据看板（每周一 30 分钟）**
一张表记录全部资产：安装/使用/成交/退款/评价数/差评要点。周环比 > 0 的资产加投入，连续 3 周零成交的下架或重做描述。**下架也是运营动作**——僵尸资产拉低品牌整体使用量均值。

**⑤ 交叉引导（写在 agent 正文里，合规）**
每个付费专家的 agent 定义末尾加一段：任务完成后按用户身份自然提示下一步（"要把这份知识库变成可卖的服务？可以试试 XX"）。不用弹窗不用广告位，引导发生在用户刚得到价值的时刻。

## 五、收入模型（按 1.6% 费率基准，费率上调做压力测试）

假设第 1 波–第 3 波共 6 个付费资产，4 周数据：

| 情形 | 假设 | 月收入（毛） | 抽成 30% 后 |
|---|---|---|---|
| 保守 | 每资产 3 单/月，均价 ¥120 | ¥2,160 | ¥1,512 |
| 中性 | 每资产 10 单/月，均价 ¥140 | ¥8,400 | ¥5,880 |
| 乐观 | 1 个资产跑出（30 单）+ 其余 5 个（10 单） | ¥12,200 | ¥8,540 |

**矩阵的真正收益不在左列数字，在第 5 列之外**：按 2% 转化估，月 8,400 毛收入 ≈ 60 个付费用户 ≈ 其中 5–10 个 B 端线索，1 单对公交付（¥2k–8k）就超过全部 C 端零售。**C 端矩阵是获客系统，对公才是利润表。**

## 六、资产仓库工程（把上架做成流水线——Owner 的工程优势用在这）

新建 monorepo `workbuddy-assets/`：

```
workbuddy-assets/
├── assets/
│   ├── narwhal-skill/          # 免费技能
│   ├── knowledge-compiler/     # 付费专家
│   ├── retrieval-advisor/      # 检索选型顾问
│   └── ...
├── shared/
│   ├── brand/                  # 统一头像生成 prompt、README 模板
│   └── validate.py             # 字段自检：40–50字 / defaultInitPrompt=quickPrompts[0] / 路径存在 / 头像尺寸
├── pack.py                     # validate 通过 → 打 zip（按 .codebuddy-plugin 结构）
└── RELEASE.md                  # 每资产一页：上架日期/版本/价格/数据
```

**关键主张：上架流程自动化是我们相对其他开发者的最大杠杆。** 平台上第一批卖家用对话手工搓包、提交、被解析失败打回；我们有 validate + pack 一条命令出合规 zip，迭代速度差一个量级。`validate.py` 第一版半天可写完，W1 就要上。

## 七、风险与红线

| 风险 | 对策 |
|---|---|
| 付费资产加密 + 云端运行 + 禁用自定义模式 | ¥1 探针验三件事：可写目录范围、加密后 `scripts/*.py` 能否执行、产物能否落到用户可见位置；若不可写则全资产改「云端生成→导出 zip」口径（Read/Write/Bash 已确认是系统内置工具） |
| 矩阵摊大，每个资产都是半成品 | 红线 ≤6 个；每波通过标准卡死 |
| 免费小技能被同行用更低质量卷死 | 不靠它们赚钱，只靠它们的使用量与评价；被卷就走 |
| 内容复用撞车（线 1 与线 3 都讲"知识变现"） | 严格按买家人群切分：线 1 卖给有经验的人（做出资产），线 3 卖给想赚钱的人（卖出去）；两线资产互不引用对方术语 |
| opc-core 候选包与「一人公司启动官」的品牌混淆 | 候选包归 Owner 个人知识体系，市场资产用公司品牌；方法论改写 ≠ 原包上架，提审节奏由 Owner 单独决定 |
