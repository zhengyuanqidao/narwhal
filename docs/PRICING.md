# Narwhal 商业化：三档定价设计（v0.1 讨论稿）

> 前提：skill 本体是 MIT 开源。**任何写进仓库的能力（BM25、图索引、aka 锚点、embedding 脚本）都不能作为收费点**——用户可以 fork 自建。
> 因此收费点必须落在**代码之外**：交付、运维、算力、隐私、持续更新。

## 一、先纠正一件事：检索档位 ≠ 收费档位

初版想法是"档1 免费 / 档2 买断 / 档3 按服务"，这个方向对，但**不能按检索档位切分**：

| 用户会说 | 结果 |
|---|---|
| "档2 就是 BM25+图索引，代码在 MIT 仓库里，我为什么要买？" | 买断站不住脚，除非卖的不是代码 |
| "档3 的 embedding 就是跑个 fastembed，我自己 pip 一下" | 按算力收费站不住脚，除非卖的是免运维 |

**结论**：档位按"**谁承担交付与运维**"切分，检索档位只作为包装里的一层技术说明。同一个检索能力，在不同档位卖的是不同东西。

## 二、三档设计（改造后）

| | 免费版 | 买断版（一次性） | 服务版（订阅/按项目） |
|---|---|---|---|
| 定位 | 分发渠道 | 交付你的库 | 持续运营你的判断力 |
| 卖的东西 | skill 本体（MIT）+ 模板 + 文档 | **一次性建库交付**：扫你的文档→分诊→聚类→生成条目/案例/MOC→编译 SOP/CHECKLIST/PLAYBOOK | 托管检索 + 持续入库 + 季度体检 + 版本管理 |
| 检索档位 | 档1（纯内存导航） | 档1 + 档2（BM25+图索引+aka 锚点），随交付物一起给 | 档2 + 档3（embedding，可选私有化） |
| 交付物 | 一个文件夹 | **你的知识库 + 你的 SOP 包**（可移植、可离线、永久可用） | 一个在跑的系统 + 每月更新的库 |
| 定价锚点 | 0 | ¥2,000–8,000 / 领域（按文档量与领域数） | ¥500–2,000 / 月，或年度 retainer |
| 成本结构 | 0 | 人力为主，毛利高但不可复用 | 算力 + 人力，需控制单位成本 |
| 关键风险 | 无 | 用户买完就走，不续费 | 续费依赖"库确实在变好" |

**为什么买断价要按"领域"而不是"套"计**：交付物是"你的私有判断力"，价值随领域数和文档量线性增长；按套定价会逼你压缩交付深度。

**为什么服务版必须保留"版本管理"作为付费理由**：知识库会腐烂（这就是 `log.md` + `OPEN-QUESTIONS.md` 的用途），"持续体检 + 编译新版本"是唯一能解释订阅费的持续价值。**不要用"更多检索能力"解释订阅**——那等于承认免费版是残废，用户会等破解。

## 三、档3 的 embedding：托管优先，私有化是高价 SKU

用户判断"档3 能部署独立 embedding 模型最好"——技术上对，商业上要分两种卖法：

| 形态 | 做法 | 定价 | 适用客户 |
|---|---|---|---|
| **托管（默认）** | 你在服务端跑共享 embedding（Qwen3-0.6B-Q，批处理 + 向量缓存），客户零部署 | 含在订阅内 | 个人/小团队，90% 的客户 |
| **私有化（高价）** | 内网部署模型 + 索引 + 权限，数据不出域 | ¥3–8 万起 + 年维保 | 有合规要求的公司 |

注意三点：
1. **模型不能写死**。e5-large（2.24GB）在基准里反而垫底，说明"体积大 = 效果好"不成立；每个客户的库都应在启用 embedding 前用他自己的语料跑一次对比（`eval/exp_retrieval_scale.py` 就是现成的工具）。
2. **向量索引要能重建**。语料更新后必须可增量重算，否则托管侧的库会长期漂移。
3. **别把 embedding 当卖点讲**。用户听得懂的是"找得到"，不是"512 维余弦相似度"——对外只说"更大的库也能秒级定位"。

## 四、这套阶梯的三个硬伤（必须先想清楚）

1. **MIT 允许竞争性托管**。任何人可以 fork 仓库去做同类 SaaS。真正的护城河是**客户自己的库**（迁移成本高）+ 交付质量 + 品牌，不是代码。可选动作：skill 保持 MIT（保住分发），托管服务、编译器、交付工具链闭源，并注册商标。
2. **买断与服务互斥**。用户买断拿到可离线运行的库后，没有理由再付订阅。解决办法是**把买断定义为"某一时刻的快照"**：交付时明确"库会腐烂"，订阅卖的是防腐服务；并让买断客户在 12 个月后按"升级包"付费（新领域/新编译版本）。
3. **免费版不能是残废**。免费版必须能独立跑通全流程（初始化→深潜→导航→体检→编译），否则失去分发意义；它缺的应该只是**规模能力**（>100 条目的检索加速）和**持续服务**，不是核心功能。

## 五、建议的验证顺序（别先写价格页）

1. 先做 **3 个真实买断单**（哪怕是朋友价）：验证"交付一个库"要多少人天，毛利是多少；
2. 再跑 **1 个季度订阅**：验证用户是否愿意为"持续体检"付费——这是整条商业假设的生死线；
3. 最后再谈 embedding 托管：只有在出现"库大到 BM25 命中率掉下来"的真实客户时才上，否则就是给自己造运维负担。

> 一句话：**卖库是买断，卖不腐烂是订阅，卖合规是私有化。** 检索算法永远免费。


## 六、开源边界：只公开档1 可行吗？

结论先说：**不可行，而且会伤自己。** 理由不是"道德上不该"，而是"技术上守不住"。

### 6.1 量化：档2 的复制成本

| 组件 | 体量 | 复刻难度 |
|---|---|---|
| BM25（tokenize + 索引 + 打分） | **40 行 / 1,328 字符** | 教科书算法，熟练工程师半天 |
| 图索引（`[[链接]]` → nodes/edges + 1 跳查询） | 130 行 | 一天 |
| aka 锚点 | **一个 frontmatter 字段名** | 讲一次就学会了，无法保密 |

一个 40 行的标准算法 + 一个 130 行的正则抽取，构不成任何护城河。**你把档2 关起来，用户看到档1 的 Markdown 结构，一周内就会自己写一个功能等价的。**

更麻烦的是：**档2 不是代码，是约定**。`aka: 亏本 亏损 不赚钱` 这行东西，你写在文档里就等于送出去；不写在文档里，用户就不知道要写——而这恰恰会让他们觉得"这破库搜不到东西"，反而伤口碑。

### 6.2 更现实的问题：已经公开了，收不回去

仓库现在 **164 个文件公开**，含 `skills/narwhal/scripts/wiki_graph.py`、整个 `eval/`（131 个文件）、以及本文档。若要改成"只公开档1"，需要 rewrite history + force push——这本身就是在向社区宣告"我们改主意了"，信任成本远高于收益。

**这条事实本身就是最好的判据**：一套你已经在公开场合演示过、评测过、写进 README 的做法，就别再想着把它变成付费墙。

### 6.3 那什么能当付费墙？

只有"复制成本 > 付费意愿"的东西：

| 候选 | 复制成本 | 能否收费 | 判断 |
|---|---|---|---|
| 检索算法（BM25/图/embedding） | 半天 | ❌ | 已公开，且不值钱 |
| SKILL.md 的方法论 | 一小时（读懂）| ❌ | 但**坚持**很难，这是软性壁垒 |
| 行业领域模板库（垂直 SOP 骨架） | 数周/领域 | ✅ | 需要真实行业经验沉淀，可售卖 |
| 一次性建库交付 | 需要人和时间 | ✅✅ | 最硬的付费点 |
| 多租户/权限/审计/并发写冲突消解 | 数周～数月工程 | ✅✅ | 企业刚需，纯工程量，可闭源 |
| 托管运维 + 持续入库 | 长期人力 | ✅✅ | 订阅的正当性来源 |
| 私有化部署（合规） | 集成 + 运维 | ✅ | 高客单 SKU |

### 6.4 推荐结构：开源核心全开，闭源"交付与规模"

```
开源（MIT，最大化分发）
├── SKILL.md                # 档1 完整方法论
├── scripts/wiki_tool.py    # 体检
├── scripts/wiki_graph.py   # 档2 图索引
├── scripts/wiki_search.py  # 档2 BM25（待做）
├── templates/              # 通用模板
└── eval/                   # 评测集（信任状：证明产出质量可验证）

闭源（商业版）
├── 多租户协作层（权限/审计/冲突消解/版本回滚）
├── 行业模板库（垂直领域 SOP 骨架，付费资产）
├── 编译器高级流程（多轮质检、领域自适应）
└── 托管服务 + 私有化部署包
```

**核心判断**：把"算法"全开源，卖"把算法用在你身上"和"替你长期跑"。这样免费用户能自力更生（他们本来就能），付费用户买的是时间和确定性。

### 6.5 如果坚持要留一道付费墙，唯一划算的做法

不是关代码，而是**关"规模"**：开源版限单库、单机、无并发；商业版做多库/团队/权限。原因是规模能力是**工程量**（数周～数月），不是**算法**（半天），复制成本差了 20 倍以上。

> 一句话：**公开档1 等于公开档2 的思想，只是让用户多花一周自己写代码——你既没收到钱，又丢了口碑。要么全开卖服务，要么全闭（那就别做开源分发）。中间态只在"规模能力"这一层成立。**


## 七、盈利模式一页纸（结论）

### 7.1 一句话盈利点

> **不卖代码，卖"替你建库"和"替你防腐"。**

代码免费（MIT），因为复制成本半天；**人的时间和客户自己的经验**才值钱。

### 7.2 四条收入线

| 收入线 | 定价 | 交付成本 | 毛利 | 作用 |
|---|---|---|---|---|
| **① 一次性建库交付** | ¥2,000–8,000 / 领域 | 2–6 人天 | ~70% | **现金流引擎**，养活自己 |
| **② 订阅 retainer** | ¥500–2,000 / 月 | 每月 0.5–2 人天 | ~60% | **估值引擎**，决定公司值多少钱 |
| ③ 私有化 / 企业版 | ¥3–8 万起 + 20% 年维保 | 5–15 人天 | ~65% | 高客单，摊薄获客成本 |
| ④ 行业模板包（数字商品） | ¥299–999 / 包 | 一次性沉淀 | ~95% | 低客单引流，验证需求 |

### 7.3 单位经济（保守估算）

```
一个买断客户：5,000 元 − 2 人天×600 = 毛利 3,800 元
若转订阅：5,000 + 12×800 = 14,600 元/年（LTV 翻 3 倍）
产能：1 人 1 个月约 8–10 个买断单 → 月营收 4–5 万，毛利约 3 万
```

关键不是单价，是**转化率**：买断 → 订阅的转化率若能到 40%，LTV 就从 5k 变 9k，公司才有估值。

### 7.4 客户为什么付钱（三条，缺一条就卖不动）

| 理由 | 客户原话 | 对应交付 |
|---|---|---|
| **省时间** | "我自己搭要两周，还不一定成" | 建库交付 |
| **挖不出自己的经验** | "我知道我懂，但写不出来" | 访谈式深潜（追问到具体阈值/反例） |
| **库会腐烂** | "上个月建的，现在没人更新了" | 季度体检 + 持续入库 |

第三条是**唯一能解释订阅的**。前两条只能卖一次性。

### 7.5 护城河排序（从硬到软）

1. **客户库的沉没成本**（迁移要重来一遍）— 最硬
2. **交付质量口碑**（同行推荐，无法压缩成代码）
3. **行业模板库**（需要真实经验沉淀）
4. 代码与算法 — 已开源，等于 0

### 7.6 获客路径（免费版就是漏斗口）

```
GitHub / skills.sh / TypingMind 收录
        ↓  免费 skill + eval 公开（信任状：产出质量可验证）
装一次，跑模式 A 建个空库
        ↓  发现"建库容易，填内容难"
买断交付 ¥2k–8k（首次变现）
        ↓  3 个月后库开始腐烂
订阅 ¥500–2k/月（持续变现）
```

### 7.7 最小验证（先做这个，别先做官网）

1. **3 个买断单**（朋友价也行）→ 测出真实人天与毛利；
2. **1 个季度订阅** → 验证"防腐"付费意愿（生死线）；
3. 两条都成立，再谈私有化与模板包。

> 若第 2 条失败（没人愿意为"保持库新鲜"付月费），说明这个产品只能做项目制外包，**不具备订阅估值**——这是必须尽早知道的结论。


## 八、token 谁出？（一次性交付到底划不划算）

### 8.1 先算账：token 在交付里只占 0.2%–4.5%

典型买断单：200 份文档 × 5,000 字 ≈ 1.0M tokens 原始语料；含流程放大（分诊通读、聚类回读、逐条写入回读源文、自检）约 **4.0M input + 48K output**。

| 模型档 | 单次交付 token 成本 | 占 ¥2,000 交付价 | 占 ¥5,000 交付价 |
|---|---|---|---|
| 国产便宜（deepseek 级 ¥2/¥8 per M） | ¥8.4 | 0.42% | 0.17% |
| 国产中档（glm/qwen 旗舰 ¥6/¥24） | ¥25.2 | 1.26% | 0.50% |
| 境外高端（¥21/¥105） | ¥89.0 | 4.45% | 1.78% |

运维阶段更低：每月增量 20 份 + 30 次查询 ≈ 290K tokens → **¥0.8–9/月，占 ¥800 订阅费的 0.1%–1.1%**。

**结论：交付和运维的 token 成本可以忽略，真正的成本是人力（2–6 人天）。**

### 8.2 但有一个会吃掉订阅费的情形

客户不按检索接口查，而是**把整库塞进对话狂问**（500 条目 × 500 tokens ≈ 250K/次，一天 20 次）：

| 模型档 | 月成本 | 对比 ¥800 订阅费 |
|---|---|---|
| 国产便宜 | ¥300 | 38% |
| 国产中档 | ¥900 | **113%（亏）** |
| 境外高端 | ¥3,150 | **394%（巨亏）** |

**这才是 token 的真实风险点，而且它不是定价问题，是架构问题。** 防御手段有三层：
1. **产品层**：档2 检索（BM25+图）把单次查询压到 2–3K tokens，而不是 250K —— **检索架构本身就是成本控制手段**，这是前面三档设计的隐藏价值；
2. **额度层**：订阅含额度（如 3M tokens/月或 100 次深潜），超量按 ¥X/M 加购；
3. **路由层**：分诊/查重用小模型，写入/编译用大模型（双模型路由，成本可再降 60%）。

### 8.3 各档位 token 由谁出（建议写进合同）

| 档位 | token 由谁出 | 理由 |
|---|---|---|
| 免费版 | **客户自带 key（BYOK）** | 零边际成本，也让客户自己对用量有感知 |
| 买断交付 | **你出，包干**（每单上限 ¥300，超出加购） | 占比 <5%，包干最省事，还能当卖点 |
| 订阅 | **你出 + 额度**（3M/月，超量加购） | 防止 8.2 的滥用情形 |
| 私有化 | **客户出**（自有 key 或本地模型） | 数据不出域，天然 BYOK |

一句话：**免费和私有化 BYOK，付费档包干+额度。** 别做"无限量"，那不是慷慨，是给自己埋亏损。

### 8.4 回到原问题：一次性交付划不划算？

**token 不是它的问题，这三点才是：**

| 问题 | 严重性 | 解法 |
|---|---|---|
| **人力不可复用** | 致命 | 规模只能靠加人，毛利不随规模改善 |
| **交付即失联** | 高 | 无复购，LTV = 单价 |
| **被拿去和外包比价** | 中 | 客户会拿"建个知识库"的市场价压你 |

所以：**一次性交付不该当利润中心，该当获客手段**——定价贴着成本走（平价甚至略亏），把利润留给订阅。或者在交付阶段就产品化：用模板库 + 批量处理把 2–6 人天压到 0.5–1 人天，毛利才真正拉开。

> 修正前文的排序：**买断是漏斗，不是引擎；订阅才是引擎。** 前文 7.2 表里"现金流引擎"的说法应理解为"启动期靠它活命"，不是长期利润来源。


## 九、编译生产知识库的成本结构

### 9.1 实测：编译的 token 成本近乎为零

以 case-01 的真实产物为基准（一个领域 ≈ 2 条目 + 1 案例 + 1 MOC = 2,219 tokens），按成熟领域（20 条目 + 5 案例 ≈ 22K tokens）外推：

| 动作 | input / output | 国产便宜 | 国产中档 | 境外高端 |
|---|---|---|---|---|
| **编译一次**（SOP+CHECKLIST+PLAYBOOK 三件套，各通读一遍领域） | 67K / 6K | **¥0.18** | ¥0.54 | ¥2.03 |
| **建库撰写**（25 条目+案例，每篇回读源材料 2 次） | 120K / 20K | ¥0.40 | ¥1.20 | ¥4.62 |
| **增量重编译**（3 条目变更） | 1.5K / — | ¥0.003 | ¥0.009 | ¥0.03 |

**整个领域的"生产+编译"总 token 成本：¥0.5–7。** 这个数字说明一件事：**token 从来不是这个生意的成本项，人的判断才是。**

### 9.2 真实成本：人天分布

| 环节 | 人天 | 能否压缩 | 压缩手段 |
|---|---|---|---|
| 采集与解析（脚本批量） | 0.1 | ✅ 已自动化 | `wiki_tool.py` + 格式抽取 |
| 分诊与聚类 | 0.3 | ✅ 小模型可做 | 双模型路由，小模型分诊 |
| 条目撰写（20–25 篇） | 1.5–3 | ⚠️ 部分 | 模板 + 批量初稿 |
| 案例复盘 | 0.5–1 | ⚠️ 部分 | 需要客户口述，难压缩 |
| **审校（防幻觉）** | **0.5–1** | ❌ **几乎不可压缩** | 这是质量底线，压了就出垃圾条目 |
| 编译三件套 | 0.2 | ✅ 已半自动 | skill-forge |
| 合计 | **2.5–5 人天** | 目标 0.5–1 | 见 9.4 |

**审校不可压缩**的原因：LLM 写的条目容易"正确但空洞"（"要重视供应链管理"这种废话）。Narwhal 的质量红线（具体阈值、具体反例、适用边界）**必须人核**——这正是"经验 > 信息"的执行成本，也是别人无法用 prompt 绕过的地方。

### 9.3 定价应该按"原料形态"分层，不按文档数量

同一领域，客户的资料形态直接决定人天：

| 原料形态 | 典型客户 | 人天 | 建议定价 |
|---|---|---|---|
| **A. 有归档文档**（周报/复盘/纪要成堆） | 有 SOP 意识的中型团队 | 1.5–2.5 | ¥2,000–3,000 |
| **B. 散落在聊天记录/邮件/云盘** | 大多数小团队 | 3–4 | ¥3,000–5,000 |
| **C. 只在脑子里**（需要访谈追问） | 个人专家/老板 | 5–8 | ¥5,000–8,000 |

按文档数量定价是错的——**1,000 份周报可能比 10 次深度访谈更便宜**。销售时先问一句"你的经验现在存在哪"，就能直接判档。

### 9.4 把 2.5–5 人天压到 0.5–1 的路径（这才是产品化）

1. **模板库**：每个垂直领域预置条目骨架（阈值位置、常见反例清单），撰写从"创作"变"填空"；
2. **批量初稿**：小模型按模板批量生成，人只做"事实核对 + 阈值确认"；
3. **把审校变成清单**：不问"写得好不好"，只查四条硬指标（有数字？有反例？有边界？有 ⭐ 一句话？）——这是可外包给初级人的工作；
4. **编译缓存**：领域条目未变更时跳过重编译（增量成本 ≈ ¥0.01），订阅侧几乎零边际成本。

### 9.5 对商业模式的两个推论

1. **订阅的边际成本极低**（¥0.01–9/月），**毛利可以做到 90%+**——前提是别让客户滥用全库上下文（见 8.2）；
2. **交付阶段是唯一的重人力环节**，所以交付必须卖"认知"而不是"工时"：客户买的是"把隐性经验变成可复用资产"，一旦按工时报价，就会被拿去和资料整理外包比价。
