# Narwhal 产品化定义（v0.1）

> 一句话：**产品化不是做一个 App，是把"专家陪跑"变成一条可重复、可计量、可交接的知识生产线。**

## 一、现状：手工作坊，不是工程

现在跑一次交付是这样的：人给一批文档 → agent 读 SKILL.md → 自由发挥 → 产出条目 → 人肉看一遍 → 交付。
问题不在质量（现在质量不错），在**不可控**：

| 症状 | 后果 |
|---|---|
| 每次产出结构靠模型自觉 | 换个模型/换个会话，质量方差大 |
| 分诊结果只在对话里 | 无法审计、无法回归、无法向客户证明 |
| 审校靠"看一眼" | 不可外包，必须你本人 |
| 人天靠感觉估 | 无法报价、无法排期、无法算毛利 |
| 无版本号 | 客户问"这次的库比上次好在哪"答不出来 |

**手工作坊的特征：质量取决于谁在做。工程的标志：质量取决于流程。**

## 二、产品化 = 七段生产线

```
① 采集 ─→ ② 分诊 ─→ ③ 撰写 ─→ ④ 编译 ─→ ⑤ 检索 ─→ ⑥ 质检 ─→ ⑦ 交付
   ↓         ↓          ↓          ↓          ↓          ↓         ↓
 指纹去重   triage.json 模板+门禁  版本+日志  三档索引   分数报告  库+报告+SLA
```

| 段 | 现在的样子 | 产品化后必须有的 | 人做 / 机器做 |
|---|---|---|---|
| ① 采集 | 手工给路径 | 格式白名单 + 解析容错（0 字符即失败）+ sha256 指纹 + 去重 | 机器 100% |
| ② 分诊 | 写在对话里 | `triage.json`（文件→经验/参考/噪音 + 理由），可审计 | 机器 90% / 人 10% |
| ③ 撰写 | 模型自由写 | 模板填空 + **四条硬指标门禁**（有数字？有反例？有边界？有 ⭐？）机器判 | 机器 70% / 人 30%（只核事实与阈值） |
| ④ 编译 | 手触发 | 门槛检查（≥5 条目+2 案例）+ 版本号 + CHANGELOG + 增量重编译 | 机器 95% |
| ⑤ 检索 | 档1 靠地图 | 档1/2 自动就位（条目过 100 自动建图与 BM25 索引） | 机器 100% |
| ⑥ 质检 | `doctor` 三项 | eval 11 项打分 + **给客户看的质检报告**（这本身是交付物） | 机器 100% |
| ⑦ 交付 | 一个文件夹 | 文件夹 + 质检报告 + 使用说明 + 3 个月维护承诺 | 人 80% |

**核心变化：把"判断"从人脑搬进检查脚本。** 人只在两个点介入——**访谈挖经验**（③ 之前）和**审校事实**（③ 之后），其余全交给流程。

## 三、判定标准：什么时候才算"产品化完成"

三条硬指标，缺一条都不算：

| 指标 | 现在的值 | 目标 | 怎么测 |
|---|---|---|---|
| **可重复** | 未测 | 同批文档跑 3 次，eval 分数方差 < 5 分 | 三次运行取 `run_eval.py` 分数 |
| **可交接** | 依赖你本人 | 一个没见过项目的人按 SOP 能跑完一个领域 | 找 1 个新人实跑，卡点计数 |
| **可计价** | 靠感觉 | 每领域人天误差 < 20%，token 成本可核算 | 记录 5 单实际人天 vs 预估 |

**"可交接"是最容易被忽略、也最能说明问题的一条**：如果只有你能交付，那就不是产品，是你在卖自己。

## 四、产品化的两个阶段（别跳级）

### 阶段 1：服务产品化（现在就该做，3–6 个月）

不写 App，只做三件事：
1. **固化交付物标准**：每个领域交付 = 库 + 质检报告 + 使用说明 + 3 个月维护；
2. **固化流程 SOP**：七段流水线写成操作手册，初级人可执行；
3. **固化报价模型**：按原料形态 A/B/C 三档报价，人天可预估。

这一阶段卖的是"标准化服务"，客户买的是确定性。**能立刻收钱，且不需要写一行前端。**

### 阶段 2：产品化到软件（有人付费验证后再做）

把流水线塞进产品，客户自助：
- 多库管理 / 团队权限 / 审计日志 / 计费
- 这层才是闭源的部分（工程量数周～数月，复制成本远高于算法）

**顺序不能反。** 没有 5 个付费客户就做 SaaS，等于用工程时间买不确定性。

## 五、不要做的事（产品化最常见的三个坑）

| 坑 | 为什么不能做 |
|---|---|
| **先做 UI/SaaS** | 需求没验证，做出来没人用；且 UI 不产生任何交付质量 |
| **追求全自动** | "一键建库"必然产出空洞条目，砸的是"经验>信息"的招牌；正确目标是**半自动 + 强制人工检查点** |
| **把流程做成黑盒** | 客户看不到质检分数就不信任；质检报告必须是对外交付物，不是内部日志 |

## 六、产品化的最小可见成果（本周就能做）

1. `wiki_search.py`（档2 BM25，与 `wiki_graph.py` 配套）—— 让 ≥100 条目的库可用；
2. `triage.json` 产物规范化 —— 让分诊可审计（也是 eval 第 2 项的基础）；
3. **一页质检报告模板** —— 交付时给客户看的那张纸（分数 + 缺口 + 下一步建议）；
4. 一条"新人按 SOP 跑一个领域"的实测记录 —— 直接验证"可交接"。

> 一句话总结：**产品化 = 让质量由流程保证，而不是由你的水平保证。**
