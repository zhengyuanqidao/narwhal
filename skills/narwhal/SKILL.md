# Narwhal — 深潜，立起你的专家身份

> Narwhal · Dive deep. Stand out.（独角鲸：深潜，成家。）
> 把散落的个人经验"深潜"成结构化知识，用知识地图与领域技能立起专家身份。这不是建百科——是把你验证过的经验编译成可复用的专家资产。

## 核心理念

1. **经验 > 信息**：只沉淀"我经历过、验证过、有独家判断"的内容，不搬运通用知识。
2. **条目原子化**：一个条目讲透一个知识点/方法/教训，500~1500 字。
3. **互联成网**：条目之间必须双向链接，孤岛条目是失败的知识库。
4. **地图优先**：先建 MOC（Map of Content），再填条目；没有地图的知识库会失序。
5. **编译而非检索**（Karpathy llm-wiki 模式）：知识编译一次、持续维护，而非每次查询临时检索；源材料不可变，条目由 agent 拥有并维护。
6. **分工**：人负责策展源材料与指方向（一次）；agent 负责摘要、分诊、聚类、交叉引用、归档、一致性维护与交付收尾。
   **默认无人值守**：自 v1.2.0 起，本技能按「安装即可自助跑完」设计——作者只在写规格时出现一次，之后每个产物由使用者的 agent 独立跑完，不要求作者或使用者逐条确认。所有"提交用户确认"改为**可选**（用户明确要求交互时才等），默认自主判定并在产物中留痕待复核。理由：一个人（OPC）无法在每次交付时在场；确认环节会把资产退化成服务。

## 领域知识库与技能输出

### 按领域组织

一个 wiki 可以包含多个**领域**（domain），每个领域是独立的子知识库：

```
wiki/entries/<领域>/   wiki/cases/<领域>/   wiki/moc/<领域>.md
```

领域由发现阶段自动聚类提出（见模式 E），最终由用户确认。领域数量控制在 3~7 个：太少说明聚类粒度过粗，太多说明需要合并。

### 领域工作技能输出（skill-forge）

领域知识库积累到一定程度（该领域 ≥5 条目 + ≥2 案例）后，可按用户指令把该领域"编译"为一个**可交付的工作技能**，产出物（默认写到 `wiki/exports/<领域>/`）：

1. **`SOP.md`** — 该领域标准作业流程：从 methods/ 和高 confidence 条目提炼，步骤化、可执行。
2. **`CHECKLIST.md`** — 该领域开工前检查清单：从 pitfall 条目反向推导（每个踩坑 → 一条检查项）。
3. **`PLAYBOOK.md`** — 实战手册：精选 cases/ 复盘（背景-做法-结果-教训），按场景索引。
4. **`BRIEF.md`** — 领域简报：我的专家主张、能力边界、可承接的任务类型（对外展示用）。
5. **`skill.md`**（可选）— 打包为 Agent Skill 格式：把 SOP+CHECKLIST+条目精华压缩成一份 SKILL.md，安装后即可在该领域工作中自动生效。

输出原则：只引用 wiki 内已验证内容，confidence 低的条目不进入 SOP/CHECKLIST；每份输出注明引用的来源条目。

## 知识库目录结构（三层架构）

知识库根目录默认为 `<工作区>/wiki/`（用户指定则从其指定）：

```
wiki/
├── SCHEMA.md                  # 第3层：约定——目录规则、条目模板引用、标签体系、领域配置
├── HOME.md                    # index：内容目录 + 每条一句话摘要 + 最近更新
├── log.md                     # 追加式动作日志（YYYY-MM-DD + 做了什么），只增不删
├── raw/                       # 第1层：不可变源材料——原文、对话记录、文档、笔记导入
│   └── <YYYY-MM-DD>-<来源名>.md
├── moc/                       # 第2层：知识地图（Map of Content），按领域一图一文件
│   └── <领域名>.md
├── entries/                   # 第2层：原子知识条目（agent 拥有，可增改）
│   └── <领域>/<条目名>.md
├── cases/                     # 第2层：经验案例：真实事情经过 + 复盘
│   └── <领域>/<案例名>.md
├── methods/                   # 第2层：个人方法论/SOP/检查清单
│   └── <方法名>.md
└── profile/
    ├── EXPERT-PROFILE.md      # 专家画像：身份定位、能力矩阵、代表作
    └── OPEN-QUESTIONS.md      # 待深潜问题清单（驱动下一轮输入）
└── exports/                   # 领域技能输出物（SOP/CHECKLIST/PLAYBOOK/BRIEF/skill.md）
    └── <领域>/
```

规则：
- **入口文件必须在 wiki 根目录**（不是 `moc/` 里）：`SCHEMA.md`、`HOME.md`、`log.md`、`triage.md`。`moc/` 只放领域地图（`moc/<领域>.md`）。放错位置会让体检判据与交付说明对不上。
- `raw/` 一经写入**永不修改**；agent 只读取，任何提炼都落到 entries/cases。
- 条目中引用源材料时，用相对链接指向 `raw/` 对应文件。
- 每次任何写操作（新建/更新/体检）结束后，**必须在 log.md 末尾追加一行**：`- YYYY-MM-DD | 模式X | 动作摘要`。

## 会话恢复仪式（orientation，每次必须先做）

面对已有 wiki，做任何 ingest/query/lint 之前，必须依次：

1. 读 `SCHEMA.md` —— 了解领域配置与约定。
2. 读 `HOME.md` —— 了解已有哪些条目及摘要，避免重复建页、漏交叉引用。
3. 读 `log.md` 最后 20~30 行 —— 了解最近做过什么。
4. 条目超过 100 篇时，先用 Grep 按关键词搜一遍，再决定新建还是更新。

## 条目模板（assets/templates/entry.md）

必填字段（YAML frontmatter）：

```yaml
---
title: 条目标题
domain: 所属领域
type: concept | method | pitfall | insight | resource   # 概念/方法/踩坑/洞察/资源
confidence: 高 | 中 | 低 | 低·外部参考   # 确信度；外部参考资料固定用"低·外部参考"（见模式 E 分诊）
source: 经验来源（项目/事件/阅读）
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
links: ["[[相关条目]]"]           # 双向链接，[[ ]] 语法
---
```

正文固定三段：**一句话结论 → 展开与个人判断 → 适用边界/反例**。

## 案例模板（assets/templates/case.md）

**背景 → 我做了什么 → 结果 → 复盘（学到什么/下次怎么做）→ 关联条目**。

## 增量生产与版本（每次交付必做）

**原则：存量不重跑。** 每次只处理「新增 / 修改 / 删除」的部分，并给每次交付一个可引用的版本号。
用 `scripts/wiki_version.py`（零依赖）：

```bash
python3 scripts/wiki_version.py <wiki> init --version 1.0.0   # 首次交付建基线
python3 scripts/wiki_version.py <wiki> diff                    # 看本次增量（不改文件）
python3 scripts/wiki_version.py <wiki> bump minor --note "..."  # 推进版本 + 写 CHANGELOG
python3 scripts/wiki_version.py <wiki> status                  # 版本 / 待办 / stale 概览
```

### 三级指纹：解决"改几个字"的误判

整文件哈希对微改的判定是"完全不同"（据此重跑整条 = 误判），所以用三层：

| 层 | 手段 | 作用 |
|---|---|---|
| L1 | sha256 | 是否变化（快路径） |
| L2 | 段落块哈希 | 变化在哪几段（定位重算范围） |
| L3 | MinHash（3-gram，48 个最小哈希） | 相似度：**微调 ≥90% / 部分重写 60–90% / 重写 <60%** |

实测：把条目里的 `1.5` 改成 `1.8`（正文出现 6 次）→ 整文件哈希判"全变"，块哈希判 6/13 块变，MinHash 判 **96% 微调** → 正确动作是**局部改这一处，不重跑整条**。

### 四类变更的处置规矩

| 变更 | 判定 | 动作 |
|---|---|---|
| 源材料新增 | 新文件 | 正常走 ingest |
| 源材料修改 | MinHash 判幅度 | **raw 不可变**：95%+ 视为"更正"，登记为 `xxx.v2.md` 并把条目 `source` 指向新版本；实质改写则新增源文件 + 重跑受影响条目 |
| 源材料删除 | 文件消失 | **不自动删条目**：派生条目转 `stale`，交用户判断保留/归档；墓碑记进 `state.archive` |
| 条目被人改过 | 哈希变但源未变 | 标 `human-edit`，**agent 不得覆盖**；微调（≥90%）保留人改，重写（<60%）先问意图 |
| 条目重命名 | SimHash 距离 ≤3 | 识别为搬家，不算"删+增" |

### 版本号规则

- `patch`：条目文字修订、局部校正
- `minor`：新增条目/案例/领域，重新编译产物
- `major`：目录结构、SCHEMA 约定变更

### 再次投料的标准动作（第二次及以后）

用户说「又加了新文件」「接着更新」「别重做」时，**走增量，不得走模式 E 重建**。零脚本版对应 §模式 G，两者规矩一致。

```bash
python3 scripts/wiki_version.py <wiki> diff      # ① 先看本次增量，不改任何文件
python3 scripts/run.py <wiki> --title "标题" --by "落款" --zip   # ③ 全量重新收尾
python3 scripts/wiki_version.py <wiki> bump minor --note "新增 N 份材料"   # ④ 推进版本
```

| 步骤 | 动作 |
|---|---|
| ① | 先做 orientation（读 SCHEMA/HOME/log），再 `diff` 圈出新增/修改/删除及其 `kind`（微调/部分重写/重写） |
| ② | 按模式 B **只处理新增与受影响条目**：新文件归档 `raw/`；同名改动登记 `xxx.v2.md` 并把 `source` 指过去；消失的文件只把派生条目标 `stale`、不自动删；`human-edit` 条目不覆盖。旧条目一律不动 |
| ③ | `run.py` 重新跑 doctor→report→human/rag 双导出→SHARE.md/index.html→MANIFEST→zip。**`dist/` 必须随每次增量刷新**，否则转发页还是上一版 |
| ④ | `bump minor`（新增条目/领域）或 `bump patch`（仅局部修订），写清「本次比上次好在哪」 |
| ⑤ | `log.md` 追加一行：`- YYYY-MM-DD | 增量 | 新增 N、更新 M、stale K、vX.Y.Z` |

三条硬规矩：**不重建 `wiki/` 目录、不重新判定领域、不覆盖人工修改过的条目**。
回话只说四件事：读了哪几份、新增/更新了哪些条目、有无 `stale`、版本号从多少到多少——不要求用户重述需求，也不列清单让人排优先级。

> 换机或只剩 `wiki/` 目录时同样适用：orientation 读的是 `wiki/` 内三个入口文件，不依赖原始素材文件夹是否还在。

## 工作流

### 模式 A：初始化（cold start）

用户第一次建库，或想从零规划时：

1. 与用户对齐：专家身份定位（"你想成为什么领域的专家"）、已有素材（文档/笔记/对话记录/网盘文件）。
2. 用素材（若无素材则用访谈提问）提炼 3~5 个**领域**，每个领域列 5~10 个候选条目与案例。
3. 创建完整目录结构（含 SCHEMA.md、log.md、raw/），并把提炼出的领域配置写进 SCHEMA.md。
4. 已有素材原样归档进 `raw/`，再从 raw 提炼第一批条目（每领域至少 1 条，宁缺毋滥，没有真实经验的领域标记为"待验证"）。
5. 在 log.md 记录初始化动作。

### 模式 B：深潜（ingest）

用户丢来一段经历/对话/文档，或说"帮我把这个沉淀下来"：

0. 先执行会话恢复仪式（orientation）。
1. **归档源材料**：原文原样存入 `raw/<YYYY-MM-DD>-<来源名>.md`，永不修改。
2. **提炼**：从 raw 中识别知识点、方法、踩坑、结论，自主判断哪些值得入库（避免噪音），并在 triage.md 留痕"未经用户复核"。仅当用户明确要求交互时才逐条确认——默认不等待。
3. **入库**：按模板写成条目/案例，并回链 raw 源文件；与现有条目交叉比对——已有则更新（增补判断、修改 confidence、标记矛盾），没有则新建并链接相邻条目。
4. **更新地图**：把新条目挂进对应 MOC；若出现新领域则新建 MOC 并更新 HOME.md。
5. **更新画像**：若本次经验提升了某项能力或新增代表作，更新 EXPERT-PROFILE.md。
6. **反哺问题**：沉淀过程中发现的空白与疑问写入 OPEN-QUESTIONS.md，向用户抛出 1~2 个值得深潜的问题。
7. **记日志**：log.md 追加一行本次动作。

### 模式 C：导航（query）

用户问"我关于 X 积累了什么"：

0. 先执行会话恢复仪式（orientation）。
1. 从 HOME.md 或 moc/ 找到相关地图 → 顺链接读条目 → 以"条目引用 + 个人判断原文"方式回答。
2. 若库中无相关内容，如实回答并建议是否把这段对话沉淀入库。

### 模式 D：体检（lint）

用户说"体检/检查知识库/lint"，或每次大额入库后主动建议：

1. 运行 `scripts/wiki_tool.py doctor <wiki根目录>`：断链、孤儿条目、缺失元数据。
2. 运行 `scripts/report.py <wiki根目录>`：内容层五项指标（覆盖率 / 溯源率 / 孤儿率 / 重复率 / 反例密度），产出可签字的验收报告。**交付前必须全 PASS，不达标先修再交**；报告须显式列出未覆盖章节，不许只说"全部达标"。
3. **矛盾检测**（脚本之外，agent 判断）：扫描同领域条目，若两条结论互相冲突，在两条条目中互相标注 `> ⚠️ 与 [[对方条目]] 存在矛盾：……` 并提交用户裁决。
4. **覆盖缺口**：对照 OPEN-QUESTIONS.md 与 MOC 中的"待深潜"，向用户报告哪些领域长期没有新条目。
5. 体检结果与修复动作记入 log.md。

### 模式 E：全域扫描（discover）

用户说"扫描我的资料/自动发现/帮我建领域库"时，从散落文档自动建领域知识库。**已有库追加新材料时不要走本模式**——改走上方「再次投料的标准动作」，否则会重新判定领域、把已有条目重写一遍。

**1. 采集**（按顺序扫描，找到什么读什么）：
- 本地：用户指定目录、`/root/uploads/`（用户上传）、`/workspace/`（工作区文档）。
- 云端：项目网盘/云文档（如 tdrive），**只读不写**——云端文件绝不修改，需要沉淀的内容拷贝进 `raw/`。
- 支持 md/txt/docx/pdf/xlsx/pptx/csv 等常见格式；二进制文档用对应工具解析为文本。

**2. 分诊**（每份文件快速打标，不精读）：
- `经验` — 我做过的事的记录（复盘、总结、周报、方案、会议纪要）→ 优先入库
- `参考` — 别人的知识/行业资料 → 只挑与用户领域相关的少数条目，标 `confidence: 低·外部参考`
- `噪音` — 无关文件 → 跳过并告知用户扫描统计（读了 N 份、经验 X、参考 Y、跳过 Z）

**混合文档拆分**（一份文件同时含"外部情报"与"我方决策/复盘"时，如竞品分析带我方调整结论）：
- 不整篇打单一标签。按段落/章节拆：外部事实段落归 `参考`（入库时标 `confidence: 低·外部参考` 并注明来源链接），我方判断与决策段落归 `经验`（正常 confidence）。
- 在 `triage.md` 用两行记录同一文件、标签不同，并各注一句"取了哪些段落"；`raw/` 仍只存一份原样副本。
- 判据：只要一段话里有"我/我们"的第一人称决策、或"据此我改成/我决定"，就是经验；纯转述他人事实的是参考。

**3. 聚类分域**：对经验类文档按主题聚类（依据：文件名、关键词、业务对象、反复出现的场景），自主选定领域（宁少勿多，允许 1 个），在 `triage.md` 写明"领域为自动判定，待复核"，并把它列为统计报告的第一条待办。**此判定必须在产物中留痕，禁止伪装成"已获用户确认"。**

**4. 批量入库**：按上条自主选定的领域走模式 B 流程逐文件深潜（每域先出 MOC 和高价值条目），自动分批续跑、不在批次之间等待人工汇报。

**5. 更新 SCHEMA.md 领域配置表与 log.md。**

纪律：
- 单次扫描最多精读 20 份文件；**超出的自动按批次续跑**（按文件名/修改时间稳定排序），不再列清单让人排优先级——排优先级会要求人在场，违背默认无人值守。每批结束把进度写入 log.md，全部批次跑完再给统计报告。
- **交互模式（可选）**：仅当用户明确说"我要自己定领域/每批给我看"时，才在分域与批次之间等待确认；默认不等待。
- 扫描结束必须给统计报告：文件来源分布、领域聚类结果、入库数量、建议的下一个深潜主题。

### 模式 F：交付导出（export）

用户说"导出/给 RAG 用/按部门分开/交付给客户/一键出成品"时：

**0. 首选一键收尾（默认路径，无需在场）**：
```
python3 scripts/run.py <wiki根目录> --title "标题" --by "落款" --zip
```
一条命令串起：doctor 体检 → report 五项验收 → human/rag 双导出 → **生成 SHARE.md + index.html 传播节点**（可转发、带落款、含"我自己也要一份"的做法）→ MANIFEST.json → 打包。
体检有问题或验收未 PASS 时**默认不产出成品**（`--allow-fail` 仅供自查）。这一步把"交付"从人力工序变成产物自带的动作：作者只在第一次写规格时出现，之后每个成品自己跑完、自己带传播节点。

> 边界：`run.py` 只处理**已编译好**的知识库（含 entries/）；编译（散文档→条目）由本 SKILL 的模式 B/E 完成，脚本不代替模型判断。找不到 entries/ 会明确报错，不假装能从原始文档自动出库。

**以下 1~5 是不用一键入口时的手工等价步骤**：

1. **先验收，不达标不导出**：
   - `python3 scripts/wiki_tool.py doctor <wiki根目录>` → 必须 0 问题
   - `python3 scripts/report.py <wiki根目录>` → 五项内容层指标必须全 PASS
2. **人读版**：`python3 scripts/export.py <wiki> --format human --out <目录>`
3. **RAG 入库版**：`python3 scripts/export.py <wiki> --format rag --out <目录> --max-chars 500`
   - 按 `##` 小节切 chunk，每 chunk 自带 `[title]/[section]/[type]/[confidence]/[source]` 元数据
   - **反例段必须独立成 chunk**——否则检索时边界条件会被正文淹没，这是 RAG 版和 human 版最实质的区别
4. **按部门/密级分开交付**：条目 frontmatter 增 `scope`、`owner`，再 `--split-scope` 导出到 `<out>/<scope>/`，无 scope 的进 `_shared/`。
   **只做标签与切分，不做运行时鉴权**——鉴权属系统层，不是本技能的职责，硬做会把工具变成集成商项目。
5. 交付三件齐备：`VERSION`（`wiki_version.py bump`）+ `CHANGELOG.md` + 验收报告。

注意：report.py 的覆盖率**排除目录/致谢/参考这类结构性章节**（它们不是知识单元）；英文按词匹配、中文按字符 2-gram，不要用字符 2-gram 匹配英文——那样任何文本都会 100% 命中，指标等于失效。

## 质量红线

- 未经用户确认的经验，标 `confidence: 低` 并注明"待验证"。**无人值守模式下**：无真人可逐条确认，经验条目统一标 `confidence: 中`（源材料已明确记录为我方决策）、参考条目标 `低·外部参考`，并在 triage.md/条目里注明"未经用户复核"；这不算违反本条，但必须在产物中留痕待复核。
- `raw/` 不可变；log.md 只追加；SCHEMA.md 是唯一结构权威。
- 不搬运网上随处可见的通用知识；通用背景最多一句话带过并给链接。
- 每次入库后必须检查：新条目是否至少链接了 1 个已有条目？没有则主动找用户确认关联。**例外**：首次建库（cold start）时库中无任何已有条目，此规则不适用——此时要求每条至少被 HOME.md 或一个 MOC 挂载（入链即可），并在同批条目间建立交叉引用；待第二批入库起恢复"链接已有条目"要求。
- **双链写法（体检判据，必须遵守）**：`[[双链]]` 必须写在**条目正文里**——frontmatter 的 `links:` 字段**不算**（doctor 只解析正文的 `[[...]]`）；链接目标必须是**目标条目的 `title` 字段原文**，不是文件名、不是领域名。MOC 的"与其他领域的关系"若指领域，写**普通文本**不要加 `[[]]`；只有指向具体条目时才用 `[[条目标题]]`。违反会导致 doctor 报"断链"和"孤儿条目"（已由零脚本版换手实测复现：仅写 links 字段 + 用领域名当链接 = 24 断链、孤儿 100%）。
- 每次更新 HOME.md 的"最近更新"区块。
- 每次交付前必须 `wiki_version.py bump`，交付物里带 `VERSION` 与 `CHANGELOG.md`——客户要能回答"这次的库比上次好在哪"。
- 不要因为一次微改就重跑整条：先看 `diff` 的相似度判定，≥90% 只改局部。
- **已有库收到新材料一律走增量**（见「再次投料的标准动作」）：禁止重建目录、重新判定领域、全量重写旧条目、覆盖 `human-edit`；每次增量后必须用 `run.py` 刷新 `dist/`。

## 写作风格

第一人称专家视角，直接、有立场（"我后来改成 X，因为 Y"），拒绝百科腔。条目结尾用一行"⭐ 一句话给三年后的自己"。
